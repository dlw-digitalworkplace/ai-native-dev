# D43 — Native ADO State mirror by adopting the project's existing states

- **Area:** Status projection (cross-cutting; config side of the D1–D15 line)
- **Date:** 2026-07-29
- **Status:** Active

## Decision
The flow can **mirror the AIND status tag into the ADO work item's native `State` field**, so board readers (PMs, functional analysts) see progress without reading the AIND tag — by **adopting the states the project already has**, never creating, renaming, or forcing our own. A **fixed AIND-status → state-category intent** lives in the flow (categories = `Proposed`/`InProgress`/`Resolved`/`Completed`, the universal buckets present in every ADO process template); the **concrete state name** comes from whatever the project defines. A new command **`/aind:map-states`** (mechanics in `scripts/aind-states.sh` — `discover`/`propose`/`write`) queries the project's actual states for the story work-item type over the ADO REST API, **auto-maps** each AIND status to the state in its category, and **prompts the human only on serious doubt** — a category with no state, or several candidates (suggest-don't-assert; the common case needs no input). The resolved map is stored as **`stateMap` in `.claude/aind.settings.json`** (shared config, D41); `aind-common.sh` surfaces it as **`AIND_STATE_MAP`** (compact JSON); `aind-status.sh` reads it and moves the native State **after** each tag write. Mirroring is **best-effort**: an unmapped status is skipped, and a failed native-State write only **warns** (and, when the calling phase passes its agent as the optional 3rd arg, emits an `observation` lesson so recurring divergence clusters in the next dream cycle). The **AIND tag stays the single source of truth**; the native State is a one-way projection, never read back by any gate or precondition. Edge/error statuses (`Intake declined`, `Intake approved`, `Needs attention`) are left **tag-only** in v1. New artifacts: `scripts/aind-states.sh`, `commands/map-states.md`; `aind-status.sh` gains an optional `[agent]` arg + the mirror step; `aind-common.sh` maps `stateMap` → `AIND_STATE_MAP`. Runtime behavior with no map configured is byte-identical to before.

## Rationale
The board's native `State` is what most humans actually read, so a flow whose state lives only in a tag is invisible to them — but the naïve fix (make the human type target state names into config) is both a burden and fragile: every org/template has a different state set, the human has to go look them up, and a typo silently no-ops. Anchoring the mapping on **state categories** is the unlock: categories are universal across all process templates, so the flow's *intent* (this phase is "in progress", that one is "done") is fixed and portable, while the concrete *name* is discovered per project. That lets us **adopt what exists with near-zero effort** — auto-resolve the obvious, ask only where a category genuinely has zero or several states. Keeping the tag authoritative and the State a **projection, not a second source of truth**, preserves the coarse/fine split of **D4**: several fine AIND phases (`Generating plan`, `Plan ready for review`, `Ready for implementation`, `In implementation`) all sit in `InProgress`, so they collapse onto one "active" state — which is exactly *why* the native State can't replace the tag (too coarse), the original **D3/D4** reasoning. Best-effort + never-block means a board hiccup (a disallowed transition, a renamed state) can never fail a phase; routing a failure into an `observation` lesson turns silent board drift into something the dreamer surfaces. Storing the map in `aind.settings.json` (not `aind.env`) follows **D41**; keeping discovery/mapping in a script with the judgment (which candidate, or skip) in the command follows "commands are thin, mechanics are scripted". The whole feature is config side of the D1–D15 line — the status model, gates, and PR contract are untouched.
