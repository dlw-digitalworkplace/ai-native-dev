# D28 — Build phase — code-revision loop

- **Area:** Build phase — code-revision loop (steer the coder from the PR; implements D27's deferred twin of D21)
- **Date:** 2026-07-01
- **Status:** Active

## Decision
**`/aind:implement` becomes mode-aware — the twin of the plan-revision loop (D21): a first run BUILDS the code PR; a re-run on a story that already has an open code PR enters REVISE mode**, so a human can *steer the coder from the PR*. Revise mode: resolve + check out the open code PR's head branch, print the **steering digest** (top-level PR comments + every review thread tagged `[OPEN]`/`[RESOLVED]` with `thread=<id>` and `file:line`, plus the reviewer's summary/SUGGESTIONs), apply **only the human-directed** changes, reply on each acted thread, commit + push to the **same** PR, then (by default) re-enter the code-review loop. **Three needs, one capability:** applying a wanted reviewer SUGGESTION the human picked after a `CLEAN` verdict, executing a human's **tiebreak verdict** after a 3-pass deadlock (Phase 4's "coder executes the verdict → one more reviewer pass → merge"), and any pre-merge touch-up — all reduce to re-entering the open PR to make directed changes. **Decisions:** (1) **entry = re-run `/aind:implement`** (mode auto-detected), not a new command — the fix half is *warm authoring* and belongs in the warm coder session (D20/D24), exactly as `/aind:plan` folds revise into the same command; (2) **autonomy = only what the human directed** — the coder applies the picked suggestion / tiebreak verdict / requested touch-up (plus any CLI instruction) and does **not** auto-apply undirected SUGGESTIONs or free-re-implement (suggest-don't-assert: the human decides *what*, the coder executes); (3) **re-review = on by default, skippable for a trivial touch-up** — after the push the coder re-enters the existing bounded (≤3-pass) review loop, matching Phase 4's post-verdict pass, but the human may say *skip* for a directed touch-up and merge directly. **State (D4):** the tag stays `In implementation` for the whole loop — a revision is more PR iteration, never a tag move; the coder **replies** on threads but **never resolves** them (resolution stays the human's merge gate, twin of D21). **Scope stops before merge** — `/aind:complete` (D27) is still the only terminal step; a plan-level problem surfaced during revision is **flagged for a human**, never silently re-planned or rerouted. **New mechanics:** `scripts/aind-revise-code-pr.sh` (`status` = detect an OPEN code PR by marker-search; `begin` = dirty-tree guard → checkout head branch → print the steering digest via `aind-review-pr.sh digest`; `push` = push the code branch to the same PR + optional comment) — thread replies reuse `aind-review-pr.sh reply`. The code-PR **marker-search** (title `(AB#<id>)` / `AIND-LINKS` work-item id) is factored out of `aind-complete.sh` into a shared `aind-common.sh` helper (`aind_find_code_prs`) that both callers reuse, each applying its own state policy (complete wants a single MERGED match; revise wants a single OPEN). `aind-open-code-pr.sh`'s re-run refusal now **points to revise mode** instead of "not supported".

## Rationale
The plan phase already proved this exact shape one phase earlier (D21): mode-aware re-run, same-PR/same-branch iteration, agent-replies-but-never-resolves, tag unmoved — reusing it for code keeps the two build/plan loops symmetric and within v0 manual scope (no automation added). Re-running `/aind:implement` (not a new command) keeps the warm/cold line clean: applying feedback is authoring, so it stays warm; the reviewer stays the cold subagent spawned exactly as before. Restricting the coder to human-directed changes is the whole point of "steer from the PR" — it makes the human the decision-maker and keeps merge-time behaviour predictable (an agent that swept up every undirected suggestion would re-assert taste the human deliberately declined). Default-on re-review closes the tiebreak path Phase 4 specified, while the touch-up skip avoids re-opening the gate on a trivial change the human already owns. Non-derivable branch (D17) forces PR-by-search, so factoring the marker-search into one helper avoids two divergent copies (DRY; the reviewer would flag the duplication) and is safe because `aind-complete.sh`'s selection is covered by unit tests re-run after the refactor. Closing the re-run refusal turns D27's interim "hand-edit the branch" bridge into a first-class, reviewable flow.
