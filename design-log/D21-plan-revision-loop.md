# D21 — Plan-revision loop

- **Area:** Plan-revision loop (implements D1's revise-in-PR path)
- **Date:** 2026-06-29
- **Status:** Active

## Decision
**`/aind:plan` is mode-aware: a first run CREATES the plan PR; a re-run on a story that already has an open plan PR enters REVISE mode** — it checks out the existing plan branch, reads ALL the PR's review feedback (top-level comments + every resolvable thread, each tagged `[OPEN]`/`[RESOLVED]` with its `file:line`), folds the open items into `plans/<id>/plan.md`, and commits/pushes to the **same** PR (posting a one-line summary as a PR comment). It never opens a second PR and never moves the status tag (stays `Plan ready for review`); the planner does **not** resolve threads — resolution remains the human's merge gate. New mechanics: `aind-revise-plan-pr.sh` (`status` = detect mode, `begin` = checkout + print feedback digest, `push` = commit/push/comment); `aind-open-plan-pr.sh` now refuses when a plan PR already exists and points to revise mode. **Refinement (2026-06-29):** on a re-run the planner also *replies* on each open thread — a clarifying question when the feedback is unclear, an "addressed — please resolve" note when the revision handled it (`aind-revise-plan-pr.sh reply <thread-id>`, which surfaces each thread's node id in the `begin` digest) — but still **never resolves** a thread, so D5's human-resolution merge gate is untouched. The plan-PR branch lifecycle is closed by a `cleanup` phase that `/aind:approve-plan` runs post-merge (deletes the remote + local plan branch, gated on the PR being `MERGED` so an unmerged plan is never dropped; the plan doc survives on the integration branch per D10).

## Rationale
D1 always specified that plan-level gaps are fixed by the planner *revising in the PR*, and D6's v0 said revisions are "re-run by hand" — but the implementation only supported initial creation, so a re-run conflicted on the branch push and `gh pr create`. This closes that gap and turns the plan PR into a genuine **multi-reviewer feedback loop**: anyone can leave comments / reply to threads, and one re-run ingests them all and updates the single PR in place. Same-branch/same-PR iteration preserves D5 (assumptions as resolvable threads gating merge) and D10 (one living plan doc per story); the agent not resolving threads preserves the human gate; not moving the tag preserves the coarse/fine split (D4). Reading feedback through `gh`'s built-in `--jq` avoids a hard external-`jq` dependency on the GitHub path. Net: D6's "by hand" becomes "one re-run of `/aind:plan`, now revise-aware," still squarely within v0 manual scope (no automation/service identity added).
