# D31 — Greenfield onboarding — the kickstart agent

- **Area:** Greenfield onboarding — the kickstart agent (pre-flow; sibling of D18)
- **Date:** 2026-07-07
- **Status:** Active

## Decision
**A human-invoked `/aind:kickstart` bootstraps a NEW/greenfield project's `.claude/` config from a guided conversation, where D18's onboarding has no code to scan.** It elicits the project across the same three lenses D18 discovers from code — functional/domain, technical layers, cross-cutting concerns — plus the operational config (integration branch, ADO/GitHub targets, intended build/test/run tooling), reading any design docs the user points it at, then **drafts** the same artifacts: one `rules/<area>.md` per **decided** area (three-lens `_TEMPLATE.md` shape), a `CLAUDE.md` importing exactly those files, **placeholder** skills carrying the *intended* build/test/run commands **marked unverified** (the toolchain may not exist yet), and a seed-rubric + env-sample copy. Procedure: orient (redirect to `/aind:onboard` if substantial code is found) → three elicitation rounds → batched/adaptive gap questions (`AskUserQuestion` for enumerable choices, prose for the domain) → **propose the whole `.claude/` tree for validation before writing anything** → write the DRAFT files → preflight → summarize with next steps. **Authority & gate identical to D18:** suggest-don't-assert (every file a clearly-marked GREENFIELD DRAFT), draft-files-not-PR, and **bounded to the config layer, never the flow** (the D1–D15 boundary). **The one greenfield-specific discipline:** because a new project's answers are often *decisions not yet made* rather than observed facts, it **never fabricates a convention to fill a gap** — an undecided point becomes an explicit `TODO`/open question in the draft, not a rule. **Packaging = warm in-session slash command** (D20's line: it authors artifacts a human reviews, so nothing to stay cold from), reusing D18's tooling (`_TEMPLATE.md`, `project-template/CLAUDE.md`, the seed-rubric/env copy, `aind-preflight.sh`) — **no new scripts**. **Complementarity:** kickstart bootstraps config *before* code exists; `/aind:onboard`, re-run once real code lands, reconciles the intended-design drafts against the actual codebase.

## Rationale
D18 turns "adopting AIND on an existing repo" from empty stubs into a grounded first draft — but a greenfield team has the opposite problem: no code, so nothing for onboarding to read, leaving them back at hand-filling stubs. A conversation is the only available source of the same three-lens picture before code exists, and eliciting it is exactly the kind of judgment a warm authoring command is for. Reusing D18's gate (suggest/human-decides), boundary (config-not-flow), and delivery (draft files reviewed before commit) avoids inventing a second trust model for what is structurally the same day-one bootstrap. The non-fabrication rule is the *essential* difference from D18 and the reason it's a distinct decision: onboarding records observed facts, so a rule it writes is grounded by construction, whereas kickstart's inputs are partly unmade decisions — allowing it to invent a convention to look complete would violate suggest-don't-assert and ship a guessed rule every agent then obeys, so undecided must degrade to a visible TODO, not a silent default. Propose-then-write (vs. D18's write-then-summarize) is the right gate here because there's no code to constrain the draft — all judgment — so a cheap validation round before authoring avoids churn. Warm-command packaging follows D20/D24's settled line (author = warm command; cold = independent verification only), and leaning entirely on D18's existing tooling keeps it a single thin command file with zero new mechanics to test — the whole feature is judgment + conversation, which is where commands are supposed to live.
