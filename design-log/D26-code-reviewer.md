# D26 — Build phase — code reviewer

- **Area:** Build phase — code reviewer (Phase 4; follows D24)
- **Date:** 2026-07-01
- **Status:** Active

## Decision
**The code-review loop is built as a cold reviewer subagent driven from inside `/aind:implement`.** The reviewer is the flow's first `agents/` occupant (`agents/reviewer.md`, `name: aind-reviewer`); `/aind:implement` spawns it (via the `Task` tool) immediately after it opens the code PR, so the **coder↔reviewer loop lives inside the warm implement session** — the coder-fix half is *warm authoring* (only that session has hot context on what it wrote), while the reviewer stays **cold** because a Task-spawned subagent gets a fresh context handed only the work-item id + PR number, never the coder's transcript (satisfies the artifacts-only re-grounding contract). **Loop:** up to **3 reviewer passes**, each a fresh cold subagent re-grounded from artifacts (PR diff+body+`AIND-LINKS` via `aind-review-pr.sh fetch`; the merged plan; **every** `.claude/rules/*.md` **and** relevant `.claude/skills/`; on re-passes, the prior open threads + coder replies); early-exit the moment a pass is CLEAN; between passes the warm coder **fixes or rebuts** each blocking finding, commits, pushes. **Severity is three-tier and the gate is deliberately strict — CRITICAL *and* WARNING both block; only SUGGESTION is non-blocking.** Convergence is protected by an objective/taste split: WARNING is an *objective* rule/threshold/skill-pattern violation with a concrete fix, anything taste-level is a SUGGESTION (never gates). **What it checks:** plan-vs-implementation (every AC, every Definition-of-done item, the task breakdown, and data contracts on the wire) **plus the full project rule + skill set** — an asymmetry with the coder, which obeys only each task's *cited* rules (D23/D24) whereas the reviewer reads them **all**, because a cross-cutting rule can be violated by a task that never cited it — plus **scope-creep as a finding** (inverting the reference planner's "don't penalise unplanned features", per D23's simplicity bias), cross-cutting concerns (auth/logging/error-handling/security/perf), and correctness/edge cases; every finding cites `file:line` + the source it violates. **Two output channels from one run:** a structured verdict returned to the orchestrator (drives the loop) and PR artifacts (resolvable inline threads for each CRITICAL/WARNING; the SUGGESTION list in the review summary body). **The reviewer authors no fixes** — no `Edit`/`Write` and it never runs `git commit`/`push` (the guarantee is structural, since `Bash` is present for `gh`). **State (D4):** the tag stays `In implementation` for the whole loop — the PR owns all iteration and a coder↔reviewer *disagreement* never moves the tag (distinct from a stuck-state). **Escalation:** after 3 deadlocked passes → a human tiebreak — a PR "human tiebreak needed" summary **and** a signed ADO work-item comment (the orchestrator posts it, signed as a new `reviewer` agent name), **tag unchanged**; a genuine reviewer *failure* (can't resolve the plan, `gh` fails) is instead a stuck-state → `Needs attention` (D12). **New mechanics:** `scripts/aind-review-pr.sh` (`fetch`/`post`/`digest`/`resolve`/`reply`); `/aind:implement` gains `Task` in its allowed-tools + the review-loop phase. **Prior art:** adopts three-tier severity, a skill-pattern-compliance dimension, and reviewer constraints from an external SENTINEL/AUDITOR reference; **rejects** its `state.json`/`plan_hash` resume (AIND's durable state is the PR + its open threads), its multi-agent `phase_outputs` handoff (one coder, D24), and a weighted 0–100% scored-audit report for the inline gate (too assertive for the suggest-don't-assert gate; a standalone `/aind:audit` is noted but descoped). **Scope ends at reviewer-approval or human-tiebreak** — no merge, no terminal `Implementation complete` (D13), and no test authoring (D8/D9); those remain the next iterations.

## Rationale
Packaging follows the warm/cold line D20/D24 drew: the reviewer is the independent **check**, so it is cold (a subagent in `agents/`, re-grounded from artifacts) — and coldness is what the gate is *for* (D7 Phase 4); the coder that fixes is *authoring*, so it stays warm. Spawning the cold subagent *from* the warm session does not break coldness, because a Task subagent's context is fresh and receives only artifacts — so the loop can sit inside `/aind:implement` (where the fix half must be, to stay warm) without leaking the coder's reasoning into the check. A standalone `/aind:review` would force the fix half to run cold, contradicting warm authoring, and the human-tiebreak re-run it would enable is itself a next-iteration (merge) concern. The strict CRITICAL+WARNING gate answers "really challenge the coder", made safe from nit-deadlock by the objective/taste split. The reviewer reading the whole rule+skill set (vs. the coder's cited-only) is the point of an independent check — it catches the cross-cutting violations a task-scoped view misses. Keeping the tag at `In implementation` and signalling a deadlock via *comment* (never the tag) preserves D4's coarse/fine split and the D7/D12 disagreement≠stuck distinction while still satisfying "visible in ADO". All mechanics live in a script (commands stay thin), and routing the reviewer's `gh`/ADO calls through scripts avoids the fresh-subagent permission re-prompt friction that D20 identified. Stopping at PR-review keeps this a single reviewable surface (the name-what's-available discipline of D15), with merge/complete/tests as clean follow-ons rather than half-built now.
