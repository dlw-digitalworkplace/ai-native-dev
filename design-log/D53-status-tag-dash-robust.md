# D53 — AIND-status tag enforcement hardened against duplicate tags (dash/spacing-robust matcher + authoritative-read write path)

- **Area:** Work-item status tag enforcement on the ADO tracker (upholds the D3/D4 single-`AIND status`-tag invariant; touches `aind-tracker.sh`'s `_ado_set_state`/`_ado_tag_value`/`_trk_norm`)
- **Date:** 2026-08-06
- **Status:** Active

## Decision
**The AIND-status tag matcher now recognises a tag by its `AIND status` namespace prefix in a way that is tolerant of the dash character and the whitespace around it, so a stray-format status tag can no longer survive a status transition unnoticed.** Reported symptom: an item intake **declined** on the first run, then **approved** on a re-run, was left carrying **both** `AIND status - Intake declined` and `AIND status - Intake approved` — two AIND-status tags, violating the one-tag invariant (D3/D4), with **no warning**.

Root cause: `_ado_set_state` strips every existing AIND-status tag and then re-verifies exactly one remains, but both steps matched the *normalized* prefix `"aind status -"*` — a literal hyphen-minus (`-`) with a space on each side. A stale tag whose separator differs — an **en-dash `–`** / em-dash `—` (from a tag hand-edited in the ADO web UI, pasted from rendered text, or written by an older build), or a spacing variant like `AIND status-Intake declined` — normalized to e.g. `aind status – intake declined`, which fails that glob. So the stale tag was **neither dropped by the strip step nor counted by the verify step**: the verify saw exactly one (the new) AIND tag, the auto-correct/warn safety net never fired, and the old tag was left behind silently. (The plain-hyphen path was already correct — even two well-formed AIND tags self-heal on the next write — which is why the fault only ever showed up as a *silent* survivor.)

The fix has two complementary halves, both in `scripts/aind-tracker.sh` — one hardens how a duplicate is *created* (the write/op-selection), the other how a stray duplicate is *cleaned up and detected* (the match). Neither subsumes the other, so both are applied.

**1. Match/detection — the matcher recognises the whole `AIND status` namespace, dash/spacing-tolerant:**
- **`_trk_norm`** additionally folds en-dash/em-dash → hyphen (byte-level under `LC_ALL=C`, so it is portable on Windows/MSYS), so every normalized comparison is dash-agnostic.
- The three detection sites — the strip in `_ado_build_desired`, the count in `_ado_verify`, and the read in `_ado_tag_value` — broaden their case glob from `"aind status -"*` to **`"aind status"*`**, matching any tag in the reserved `AIND status` namespace regardless of the dash or the spacing around it.
- `_ado_tag_value`'s value extraction folds dashes first and treats the separating hyphen as optional (`status[[:space:]]*-?[[:space:]]*`), so the bare state value is recovered cleanly from every variant.

**2. Write/op-selection — `_ado_set_tags` reads authoritatively and picks add-vs-replace by field existence:** the read of the current tags is now a full `az boards work-item show --output json` that **fails loud** (`aind_die`) on error, rather than `_ado_read_tags`'s `--query … -o tsv 2>/dev/null || true`, which *swallows* any error and returns an empty string. An empty read wrongly selected `op=add`, and a JSON-Patch `add` on `System.Tags` **merges** into the existing tags on some builds → the exact duplicate this function exists to prevent. `op` is now chosen by whether the `System.Tags` **field exists** (`.fields | has("System.Tags")`) — the correct JSON-Patch condition (`replace` needs the path present) — instead of by the tag *string* being non-empty. Both jq reads are CRLF-stripped, because Windows jq emits `\r`: an un-stripped `has_tags` of `"true\r"` would compare unequal to `"true"` and fall straight back into the merging `add`.

## Rationale
`AIND status` is a **reserved namespace** — no legitimate non-AIND tag begins with it — so matching the whole prefix rather than the exact `AIND status - ` punctuation is both safe and more faithful to the invariant's intent: *there is at most one status tag, whatever its exact glyphs*. Keeping the enforcement centralised in `_ado_set_state` (layered on `_trk_norm`) means the strip, the verify, and the state read all agree by construction; broadening only the glob (rather than, say, rewriting tags on read) is the minimal change that closes the silent-survival gap without touching the write path or the flow. Dash folding is done at the byte level under `LC_ALL=C` because MSYS handling of multibyte characters inside `sed` bracket expressions is unreliable (the same class of Windows gotcha the tracker already works around elsewhere). This is a pure hardening of an existing invariant — the flow, status model, gates, and PR contract are untouched; only which tag strings count as "the AIND status tag" changes.

## Status / validation
Offline-validated: the updated strip/verify/extract logic was exercised against the plain-hyphen, en-dash, no-space, and mixed-with-other-tags inputs — every case now resolves to exactly one `AIND status - <state>` tag and verifies `count=1`, while a same-format merged duplicate still reports `count=2` so the retry/warn safety net fires; value extraction recovers the bare state (`Intake declined`, `Ready for intake`, …) across all dash/space variants; the `has("System.Tags")` op-selection returns `replace` for a field-present item and `add` only when the field is absent, and is CRLF-safe; `bash -n` clean. Live-validate next on a real ADO item: (a) seed an en-dash status tag and confirm a transition leaves exactly one tag, and (b) confirm the field-existence op-selection picks `replace` on a tagged item (no merge) and `add` on a brand-new item with no tags.
