# D40 — Parallel work — close-out returns the session to the main checkout

- **Area:** Parallel work — close-out returns the session to the main checkout (refines D37's drive-from-main teardown)
- **Date:** 2026-07-22
- **Status:** Active

## Decision
**`/aind:complete` and `/aind:approve-plan` now `cd` the session back to the main checkout as their first step (in worktree mode), via a new `aind-worktree.sh main-root` verb, before running any teardown.** D37's drive-from-main model assumed the session cwd stays on the main checkout (scripts enter a worktree only in a subprocess), but the coder grounding tells `/aind:implement` to run every build/test/git command with `cd "<worktree>"` first — and the host shell's working directory **persists** across commands, so the session ends the phase parked *inside* the worktree. Running close-out from there had two failures: (1) `git worktree remove` refused (a process cannot delete its own cwd — the visible symptom, worked around by a manual `prune`), and (2) **silently worse**, the cleanup script inherited that cwd so `git rev-parse --abbrev-ref HEAD` reported the worktree's *code branch* rather than the integration branch, and the "leave the dev on an up-to-date integration branch" **fast-forward was skipped** — leaving the local main checkout behind origin (the terminal tag + note still succeeded, being cwd-independent ADO writes, so the item looked complete while main was stale). The fix must be **agent-executed** (`cd` in the command markdown): only moving the *parent* session shell out of the worktree frees the OS lock and re-points the cleanup's git ops at main — a subprocess `cd` inside the script cannot do either. `main-root` exposes the existing `aind_wt_main_root` helper (resolves the main checkout from inside a linked worktree via `git rev-parse --git-common-dir`). The `/aind:plan` and `/aind:implement` grounding notes were corrected — they had claimed "your session's cwd stays on the main checkout," which is not true in a persistent shell; the honest contract is "work in the worktree freely; close-out returns to main for you." `prune` stays as the safety net for a genuinely stranded worktree (another shell sitting inside it, interrupted run). Offline-validated (`main-root` from main and from inside a worktree; parked-in-worktree → return → clean `remove`).

## Rationale
The clean teardown path (`remove` → delete branch → fast-forward integration) was degrading to a warn-then-`prune` dance on every parallel run, and — the real reason to fix rather than tolerate — the skipped fast-forward broke D37's "ends on main with latest" promise in a way that was invisible (no error, correct tag). The constraint that only a parent-shell `cd` can free the cwd lock forces the fix into the command layer rather than the scripts; a dedicated `main-root` verb keeps the commands from hand-rolling `dirname "$(git rev-parse --git-common-dir)"` and reuses the already-tested helper. Correcting the grounding notes removes a false invariant a future reader would otherwise trust. Pure config/packaging-side refinement of D37; the flow, status model, gates, and PR contract are untouched.
