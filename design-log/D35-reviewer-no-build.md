# D35 — Build phase — the reviewer does not run build/lint/test

- **Area:** Build phase — the reviewer does not run build/lint/test (bug fix; relates to D26, D33, D34)
- **Date:** 2026-07-09
- **Status:** Active

## Decision
**The cold reviewer reviews by _reading_ the diff and must not run the project's build/lint/test/run commands; only the coder runs them (pre-PR, `/aind:implement` A6).** The bug: `agents/reviewer.md` granted `Bash` (needed for the `aind-review-pr.sh` mechanics) and told the reviewer to read `.claude/skills/` for mandatory patterns — but never said whether to *run* the build/lint/test commands those skills describe, so the reviewer improvised and ran them on every pass, redundantly re-doing the coder's A6 self-check up to 3× per story. This contradicts the reviewer's design: its independence is a **cold read of the diff** (D26), and its test-quality judgment is explicitly *"a passing suite is never evidence — check each assertion against the spec, not against what the code does"* (D33), so a green run buys it nothing and must not lower its skepticism regardless. Running the build again also duplicates the coder's pre-PR objective gate (the flow's build-green gate lives with the coder, D34) and would land in project CI if a project chose to re-check it (also D34). Fix is **prompt-only** (`agents/reviewer.md`): a new Constraint §7 ("review by reading, don't run the build/tests" — a code that can't build / a test that can't pass is a *finding to report with `file:line`*, not something the reviewer executes), a clarifier on the skills-reading step ("read for the *patterns*, don't run the commands"), and a note on the Bash line that Bash is for the plugin scripts only. Considered and rejected: letting the reviewer run the build *once* when it suspects A6 was skipped — a green result still isn't evidence for a gate whose whole discipline is spec-anchored reading, the rare "coder opened a PR on broken code" case is caught at the human merge / project CI, and a conditional carve-out just reopens the ambiguity the fix closes.

## Rationale
The reviewer's value is *independence of judgment*, not re-execution: it re-derives expected behavior from the spec and checks the diff against it. Re-running the build/tests adds no signal a spec-anchored read doesn't already need (and D33 forbids treating a green suite as evidence), while costing a full build/lint/test cycle on each of up to 3 passes — pure waste multiplied by the review loop. The objective "does it build / are tests green" gate already has an owner: the coder, before the PR (D34); the reviewer duplicating it blurs the coder-gate / reviewer-gate split that D34 just clarified. The under-constrained prompt was the root cause — `Bash` + skills-that-list-commands with no explicit boundary reads as tacit permission — so the fix is to state the boundary, not remove a tool the mechanics need. Prompt-only, no script/flow change; the status model and PR mechanics are untouched.
