# D22 — Second host — GitHub Copilot CLI

- **Area:** Second host — GitHub Copilot CLI (cross-cutting; packaging)
- **Date:** 2026-06-30
- **Status:** Active

## Decision
**The plugin runs on BOTH Claude Code and GitHub Copilot CLI from one repo, with no behavior fork** — identical `commands/`, `skills/`, and bash `scripts/` (the single source of behavior). Only two things differ per host, both packaging: **(1) Manifest** — `.claude-plugin/plugin.json` (Claude) and `.github/plugin/plugin.json` (Copilot) coexist; each points its own `hooks` field at its own hook file. Copilot prefers `.github/plugin/plugin.json` and ignores `.claude-plugin/`; Claude reads only `.claude-plugin/`. **(2) Hooks** — the one genuine format incompatibility. Claude: `hooks/hooks.claude.json` (`PreToolUse`/`matcher`, command reads `{tool_input:{command}}` on stdin, blocks via **exit 2**) → `check-claude-comment.sh`. Copilot: `hooks/hooks.copilot.json` (`version:1`/`preToolUse`, `bash`+`powershell` keys; reads `{toolName,toolArgs}` on stdin, returns a `permissionDecision` JSON, **never exit 2**) → `check-copilot-comment.ps1`/`.sh`. Both load **only via explicit manifest** — the bare conventional `hooks/hooks.json` is removed so neither tool auto-discovers the other's file. `${CLAUDE_PLUGIN_ROOT}` is unchanged (Copilot injects it alongside `PLUGIN_ROOT`/`COPILOT_PLUGIN_ROOT`). **Prerequisite (Windows):** Copilot's shell tool is PowerShell, so **Git's `bash` must be the `bash` that resolves** in the launching shell — and it must win over Windows' `System32\bash.exe` (WSL launcher), which sits on the machine PATH ahead of any user-PATH entry, so a user-PATH *append* of `Git\bin` is insufficient; **prepend** it (e.g. via `$PROFILE`) and verify with `(Get-Command bash).Source`. Install with `copilot plugin install <owner>/<repo>` (commands namespace identically, `/aind:*`).

## Rationale
Empirically (live testing, Copilot CLI 1.0.65), almost everything ports unchanged: the manifest is read directly, commands register **with their `/aind:` namespace**, scripts are provider-agnostic, and `${CLAUDE_PLUGIN_ROOT}` resolves. The **only** true incompatibility is the hook config schema + I/O contract — so the minimal, honest split is a per-tool hook file behind a per-tool manifest, leaving one behavior layer untouched. Removing the conventional `hooks/hooks.json` (and naming both files explicitly) eliminates the original breakage — Copilot tried to parse the Claude-format `hooks.json` and errored, which (preToolUse errors → deny) blocked *every* tool call. Now nothing is auto-loadable to collide. The bash-on-PATH prerequisite is non-negotiable: without `bash`, the Copilot model either **reimplements the scripts in PowerShell** (silently violating the single-`AIND status`-tag invariant of D4 and the signed-comment rule — observed: duplicate tags + an unsigned comment via ad-hoc `az`/REST) or **gives up mid-run** — both worse than a clean stop. The hook port preserves signing enforcement on the Copilot side; the dual design keeps Claude's working path byte-for-byte. Net: a packaging change on the config side of the D1–D15 line; the flow, status model, and gates are untouched.
