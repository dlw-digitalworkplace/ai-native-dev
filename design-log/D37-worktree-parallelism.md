# D37 — Parallel work via AIND-owned git worktrees

- **Area:** Parallel work via AIND-owned git worktrees (config/packaging side of the D1–D15 line; relates to D22, D36)
- **Date:** 2026-07-15
- **Status:** Active

## Decision
**A project can work multiple stories at once from one clone by opting into per-phase git worktrees; AIND owns the plumbing in portable bash, no dependence on any host's native worktree feature.** Opt-in is the **presence of `.claude/aind-worktree.config.json`** (`worktreeRoot` default `.claude/worktrees`; a `copyFiles` list of the gitignored files a fresh worktree lacks — `aind.env`, `settings.local.json`, project `.env`). Every PR-creating path runs in its own worktree keyed `<id>-<phase>`: `/aind:plan`→`<id>-plan`, `/aind:implement`→`<id>-impl`; `/aind:approve-plan` and `/aind:complete` retire them. **`/aind:dream` is deliberately excluded** — the dreaming phase is an occasional, cross-story improvement flow, not per-story parallel work, so it stays single-tree (its lesson emission already uses no checkout via orphan-branch plumbing; only its synthesis config-PR touches the tree, and it is run standalone from a clean main checkout). Not an oversight — a scoping decision. **Session model = drive-from-main (chosen over hub+worktree and native `--worktree`):** every session's cwd stays on the **main checkout** and *drives* a worktree by path, because a process cannot remove its own cwd worktree (hard-locked on Windows) — so close-out, which removes the worktree → deletes the branch → fast-forwards integration, must run where cwd is never the target. Parallelism comes from multiple main-checkout terminals, each driving one story. New `scripts/aind-worktree.sh` (`enabled`/`root`/`path`/`ensure`/`ensure-plan`/`list`/`remove`/`prune`); the PR scripts gain a one-line worktree branch that cds into the worktree in their own subprocess (session cwd untouched) and are otherwise unchanged; teardown folds into the existing `aind-*-pr.sh cleanup`/`aind-complete.sh cleanup` paths. **Strict single-tree no-op when the config file is absent** (regression bar). Two Windows constraints handled: jq emits CRLF (strip `\r` off every parsed value) and `git worktree list` prints native `C:/` paths while our helpers use MSYS `/tmp` (normalise the root via `cygpath -m` for the prefix filter). **Coder grounding is the load-bearing mitigation of drive-from-main:** `/aind:implement` pins the worktree path as the coder's project root (cd there per shell, worktree-rooted file ops) with a main-tree-clean guard so a wrong-tree edit fails loud (and, since commits go through the worktree, a stray main edit is simply missing from the PR, never silently committed). **Large dirs (`node_modules`) are deferred to the project** (pnpm recommended); a portable `symlinkDirs` extension is named-not-built. **Distinct from D22's agent-host axis and D36's code-host axis** — this is a working-tree-layout axis; the flow, status model, gates, and forge are untouched.

## Rationale
Bending the flow around a host's native worktree feature (Claude Code's `--worktree`) kept hitting friction — Claude-only (breaks the D22 dual-host + future-CI story), cedes branch naming (fights the id-keyed PR-reached convention), a session-scoped human-launch lifecycle, `.worktreeinclude`⇔`WorktreeCreate` mutual exclusion, and it still doesn't solve self-removal — so the honest shape is AIND owning portable git plumbing, exactly as D36 concluded for the code host ("git is host-neutral; script it"). Per-phase over whole-item, inside-repo over sibling, and folded-into-the-phase-commands were the user's calls; drive-from-main was chosen once it was clear no session model repeals the "can't delete your own cwd" constraint — so the design routes teardown to the main checkout plus a `prune` net rather than pretending a worktree session can clean itself up. Presence-of-config as the switch (over an env var) matches "config available when opted-in" and keeps the single-tree path byte-for-byte. The CRLF and path-form fixes are the same Windows family already documented for the other scripts. Sits cleanly on the config/packaging side of the D1–D15 line, like D22 and D36.
