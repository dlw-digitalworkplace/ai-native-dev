# D25 — Generic dev knowledge — companion standards plugin

- **Area:** Generic dev knowledge — companion standards plugin (config side of the D1–D15 line; cross-cutting)
- **Date:** 2026-06-30
- **Status:** Active

## Decision
**Generic, reusable developer guidance — SOLID principles, ".NET Core usage", house coding style, and the like — does NOT ship in the AIND plugin. It lives in a separate, composable `dev-standards` plugin** (org-flavoured — e.g. one installed alongside AIND across all of an org's repos), shipping **skills** (reusable knowledge an agent pulls in), **not** flow commands. AIND itself stays domain/stack-agnostic (D11, D23). **Consumption reuses D11's two-layer pattern:** the standards plugin is the reusable **baseline** (a `solid-principles` / `dotnet-core` skill); the project's `rules/*.md` are the thin **specialization** on top — a rule *references* the relevant skill and adds the project's own exceptions plus its "what done looks like" bar, instead of restating the principle. Because the planner's tasks already cite `rules/*.md` (D23) and the coder obeys the cited rules (D24), the flow reaches the generic knowledge **through** the project rule that cites the skill — **no new flow contract is added**. **Onboarding (D18) wires the link:** when it detects a stack (e.g. .NET), it drafts rules that cite the companion skills and reports the companion plugin as a setup prerequisite. **Granularity:** start with a **single org-level standards plugin** holding stack-scoped skills; splitting into per-stack plugins is a later option if an org's stacks diverge enough to warrant it (a packaging detail, left open like other tuning calls).

## Rationale
Bundling stack knowledge into AIND would directly contradict the agnostic identity the planner and intake are built on (D11 "criteria-agnostic"; D23 "never hardcode a project's domains") and the portability rule (no stack values in the plugin): a Python team would carry .NET dead weight, and a single SOLID tweak would churn the *flow* plugin's version. Generic guidance sits on the **knowledge** side of the flow-vs-knowledge split — the same side as project rules; the only thing separating it from a project rule is **cross-project reusability**, which is exactly what makes it a *composable plugin* rather than AIND-core or per-project config. Plugins compose (both Claude Code and Copilot load several), so AIND + dev-standards + the project's own `.claude` stack cleanly, each versioning on its own cadence. Reusing D11's shipped-baseline + project-extension shape avoids inventing a new mechanism and keeps the project rule the single thing the flow cites — the standards skill is *referenced*, never duplicated into the flow. Shipping skills (not commands) matches "what can be scripted/skilled should be" and keeps commands reserved for the flow. Wiring it through onboarding turns "get my team started" into one documented install plus auto-cited rules, with zero stack knowledge baked into AIND. Starting with one plugin avoids premature fragmentation; the per-stack split stays available as a later packaging choice.
