# D45 — Onboarding rule depth, convention capture, and conflict resolution

- **Area:** Project onboarding (pre-flow; config layer) — extends D18, mirrors into D31
- **Date:** 2026-07-30
- **Status:** Active

## Decision
`/aind:onboard` (and its greenfield twin `/aind:kickstart`, D31) are sharpened so the **first draft** captures a project's real rules instead of a shallow repo map — driven by live-run feedback where a good result took six rounds of the human hand-feeding examples. D18's three-lens, evidence-only discovery is unchanged; **how deeply and in what voice** onboarding writes rules is what changes. Seven adjustments, all prompt/template only (`commands/onboard.md`, `commands/kickstart.md`, `project-template/CLAUDE.md`, `project-template/rules/_TEMPLATE.md`):

1. **Read existing agent-instruction files first.** The survey now opens `.github/copilot-instructions.md`, `.github/instructions/*`, `AGENTS.md`, a root `CLAUDE.md`, `.cursorrules`/`.cursor/rules/*`, `.windsurfrules`, `CONTRIBUTING.md` **before inferring anything**, and treats them as authoritative evidence to fold into rules (an instruction file describing a convention is sufficient evidence for that rule area — e.g. a documented docs standard → a `documentation.md` rule).
2. **A mandatory representative-source read.** Manifests and directory listings reveal only the *map*; onboarding must open a bounded, **representative sample of the project's real units** (adapted to project type — services/endpoint/component/hook for a web app, public API + modules for a library, whole scripts for a script collection, …) plus the style-encoding tooling configs.
3. **A distinct functional/domain reading pass** (the most-missed lens). Trace the **core domain abstraction and its extension model**, the main flow, the entities/invariants, and — highest-value — **how you add a new unit of the domain** (a new connector/mini-app/plugin/command). Lens 3 in step 2 is strengthened and a **completeness guard** requires either a functional rule or an explicit reason none exists (surfaced in the summary).
4. **Rules written as directives, not hedged observations.** The *draft as a whole* remains the suggestion the human prunes (DRAFT banner + review), but each rule that stays is a **requirement** ("new abstractions **must** live in `Contracts/`", grounded in a cited file) — the planner/reviewer enforce it, so "some code observes X" is unenforceable. The DRAFT banner is reworded so it no longer reads "Suggestions, not ground truth".
5. **A stack-agnostic convention checklist** (logging, error handling, naming, folder/module roles, abstraction placement, wiring/DI, imports, I/O patterns, state management, a unit's public contract, validation, lint baseline) framed as *a prompt to think with, not a boundary* — translate to whatever the project is, and where tooling already enforces a rule, point to the tool rather than restate it.
6. **Conflict detection + interactive resolution.** When the repo has competing patterns for one concern, onboarding surfaces each **material** conflict during the run via `AskUserQuestion` (a copy-pasteable candidate rule per option, recommended first), writes the chosen option as the imperative rule, and keeps the alternatives as a **Convention decision** note. Immaterial/tooling-normalised inconsistencies are just noted.
7. **Required SKILL.md frontmatter.** Every stubbed skill must carry `name` (matching its directory) **and** `description` (+ `allowed-tools` for a command-runner) — a missing `name` triggers a host "Skill should provide a name" warning. This composes with the D18-era test-skill evidence bar (a configured runner with no test artifacts is stubbed but flagged **UNVERIFIED in the `description`**, not just the body).

`project-template/CLAUDE.md` is also restructured so **project context + rule imports lead** and the AIND config is a compact operational layer beneath (worktree/telemetry detail replaced by pointers to `aind.settings.sample.json` / GETTING-STARTED), so the file reads as "how we work in THIS project" rather than an AIND template. Validated across successive live Copilot-CLI runs on a real .NET + React repo: the final run produced backend/frontend/connectors/documentation/testing rules first-pass — including the functional `connectors.md` with its extension recipe, in imperative voice, with correctly evidence-based skills — with no content pushback.

## Rationale
The recurring failure was not *wrong* rules but *shallow* ones: onboarding stopped at "keep code in the right layer / match naming" and left the actual coding conventions (structured logging, interface placement, folder roles, the connector extension model) for the human to extract by hand. The root cause was that the guidance only told the agent *which areas* to consider (D18's three lenses), never *to read real source* or *what depth of convention to capture* — so an attention-follows-detail model produced map-only rules. The fixes add that missing depth guidance without touching D18's boundaries: still evidence-only (no fabrication), still suggest-don't-assert (the *draft* is the suggestion; the *rule text* is imperative because it will be enforced), still config-layer-only. Reading pre-existing instruction files first is the cheapest possible win — a human already distilled the conventions, and re-deriving them from scratch both wastes effort and misses them. The functional-lens completeness guard converts a silent, high-variance miss into a stated decision, which is the realistic ceiling for a prompt fix: model variance can't be eliminated, but a miss can be made *visible*. Interactive conflict resolution is the one behavioural addition — a repo with two competing patterns can't be resolved by evidence alone, so the human picks and onboarding bakes the choice in as one enforceable rule (the alternatives recorded for audit), instead of silently choosing or burying a vague note. The CLAUDE.md restructure fixes a template-rooted defect: a project file dominated by plugin boilerplate buries the guidance agents most need. All of it is the config side of the D1–D15 line — the flow, status model, gates, and PR contract are untouched; the dreamer (D16/D30) remains the mechanism for the long tail these first-draft improvements don't catch.
