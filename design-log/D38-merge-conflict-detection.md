# D38 — Build phase: merge-conflict detection + a rebase resolution path in the review loop

- **Area:** Build phase — merge-conflict detection + a rebase resolution path in the review loop (relates to D26, D33, D37)
- **Date:** 2026-07-16
- **Status:** Active

## Decision
**The cold reviewer now checks, every pass, whether the code PR still merges cleanly into the integration branch, and flags a conflict as a blocking finding; the coder clears it by rebasing onto integration and force-with-lease-pushing, then hands back for a fresh pass.** Parallel work via worktrees (D37) makes this a real, recurring case: a PR that was mergeable at build time goes **conflicting** the moment another PR merges under it, and nothing in the loop noticed. **Detection is a PR *read*, not a run** — mergeability is a property the host computes (`gh` `mergeable`; ADO `mergeStatus`), so it fits the reviewer's cold, read-only, "review-by-reading-not-executing" contract (D35) exactly: a new forge verb `forge_pr_mergeable` normalises both hosts to `MERGEABLE|CONFLICTING|UNKNOWN` (D36 adapter — never call `gh`/`az` directly), surfaced through `aind-review-pr.sh` (the reviewer's one allowed Bash) in `fetch` and a new polling `mergeability` phase. Because both hosts compute mergeability **asynchronously**, `UNKNOWN` is polled briefly and then treated as **non-blocking advisory** (only a confirmed `CONFLICTING` blocks) so a transient recompute never deadlocks the loop. The conflict finding has no `file:line`, so it is the one finding documented in the **summary** (not an inline thread) under the synthetic locus `merge:integration`. **Resolution fixes a recorded lesson (57-coder):** `aind-revise-code-pr.sh` gains a `rebase` phase (fetch integration, rebase the PR head, leave conflicts in the tree for the coder to resolve in-context) and its `push` becomes **force-with-lease-aware** (a rebase rewrites history, so a plain push is rejected non-fast-forward — the push now detects the diverged remote via `merge-base --is-ancestor` and force-with-leases only then, plain fast-forward otherwise). **Kept reactive, not proactive** (the coder does *not* pre-emptively rebase before every push) — smallest change matching the observed flow; prevention (auto-rebase to reduce conflict frequency) is named-not-built. **Offline-validated then live-validated end-to-end (2026-07-17)** on a real conflicting PR: the reviewer flagged `CONFLICTING`, the coder rebased onto integration and force-with-lease-pushed, and the re-review returned `CLEAN`. Distinct axis from D22 (agent host) and D36 (code host); the status model, gates, and PR contract (D4/D5/D13/D17) are untouched — this is loop mechanics on the config side of the D1–D15 line.

## Rationale
Merge conflicts are the predictable cost of the parallelism D37 unlocked, so the flow had to grow a way to see and clear them. Making the reviewer the detector (over a separate command-level gate) matches how the loop already works — the reviewer is the judgment gate on the PR and already posts blocking findings the coder clears — and, crucially, mergeability is a *read* of host-computed state, so it does **not** breach the D35 "reviewer reviews by reading, doesn't run build/tests/git" contract the way a reviewer-run `git merge` would. Routing the query through the forge adapter (D36) keeps commands/agents host-blind and the `CONFLICTING/MERGEABLE/UNKNOWN` vocabulary in one place. Treating async `UNKNOWN` as advisory (not blocking) is the same "don't gate on a transient/uncomputed signal" discipline as the intake dependency gate's `UNKNOWN` verdict — blocking on it would cause false-positive rebases and could deadlock the 3-pass loop. The force-with-lease-aware push is the direct, minimal remedy for the exact failure the emitted lesson recorded (a rebase's non-fast-forward push falling back to a manual `--force-with-lease`), made safe by scoping the force to the coder-owned branch and only when history actually diverged. Reactive-over-proactive was chosen to keep the change small and honest to the user's observed flow; proactive rebasing trades more history churn for fewer conflicts and can be added later if the frequency warrants it.
