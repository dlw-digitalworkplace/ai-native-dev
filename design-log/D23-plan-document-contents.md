# D23 — Plan document contents

- **Area:** Plan document contents (planning / phase 1)
- **Date:** 2026-06-30
- **Status:** Active

## Decision
**The plan markdown gets a richer, fixed template so it carries enough for a coding agent to execute without re-deriving decisions — while staying domain-agnostic.** Headings, in order: **Context**; **Keep it simple** *(conditional)* — explicit non-goals plus the simpler option taken over a heavier one, dropped when there is nothing real to fence off; **Implementation approach**; **Data contracts** *(conditional)* — only when the change crosses a boundary (API↔client, service↔service, module↔module), pinning exact field names/types/nullability + any mapping, expressed in the project's own language(s), and **never fabricated** for a change with no boundary; **Task breakdown** — an ordered (dependency-first) task list where **each task cites the project rule file(s) (`.claude/rules/*.md`) it must obey** instead of being filed under a fixed domain bucket; **Assumptions & open questions** (unchanged role, D5); **Considerations** — non-blocking reviewer FYI only; **Testing recommendations** (unchanged, D8/D9); **Definition of done** — a checklist every item of which traces to a real source (an acceptance criterion, a cited rule's "what done looks like" bar, an invariant, or a ratified testing decision); **Files/areas affected**. Supporting changes: the planner also reads **project skills + `docs/`** (not just rules + code) when grounding and respects a multi-project/deployment topology where the rules define one; it is instructed to **bias toward the simplest change that satisfies the ACs** (no speculative abstraction/config/generalization); and the **Considerations-vs-open-questions boundary has a tie-breaker — anything a reviewer could reasonably want done differently is an open question (→ resolvable thread / merge gate), not a consideration; when in doubt, prefer the open question.** Revise mode keeps every new section honest on re-runs. Config side of the D1–D15 line: no flow/status/gate change; D5/D10 (assumptions-as-threads, living plan doc) and D8/D9 (two testing recommendations) are untouched.

## Rationale
The first template (Context / Approach / Assumptions / Testing / Files) proved too thin for a coding agent — it lacked an executable task decomposition, an explicit definition of done to validate against, and the cross-boundary **data contracts** that prevent front-/back-end property-name drift (the failure mode an external reference planner targeted by making data contracts first-class). The improvements adopt those ideas but keep the plugin **domain-agnostic**, mirroring D11's "rubric is data, command is procedure": the command never enumerates domains — tasks **cite** whatever `rules/*.md` the project actually has. Rule-citation beats domain-as-section because tasks order by dependency and some are cross-cutting (a task may cite >1 rule), so binding a task to its rules — not grouping it under one — is what makes the coder apply the right conventions and the right "done" bar; the Definition of done then aggregates exactly those cited rules' bars. The simplicity bias + Keep-it-simple section counter the LLM tendency to over-engineer (live-confirmed: the planner **declined an unrequested shared-nav-config refactor it had previously proposed**, recording it as a non-goal). Conditional sections with "drop rather than fabricate/platitude" stop the richer template from emitting filler on small stories. The Considerations tie-breaker closes a gap found in testing, where a borderline decision with a real alternative (selection-highlight on overflow routes) was filed as a non-gated note instead of a resolvable thread. **Explicitly NOT adopted** from the reference planner (each conflicts with AIND): "ask for clarification / don't make assumptions" (the planner never blocks — proceed-on-assumption + threads, D5); an in-doc `Status:` line (would compete with the single AIND tag, D4); per-task acceptance criteria and a fixed named-agent roster (consolidated into the rule-cited Definition of done; build-phase checks are cold and selected by rule, not named in the plan). Live-validated end-to-end on a real story (AB#19).
