# D45 — Pluggable work-item tracker — a local markdown-file backend as an alternative to Azure DevOps Boards

- **Area:** Pluggable work-item tracker — a local file store as an alternative to Azure DevOps Boards (cross-cutting; packaging, config side of the D1–D15 line; relates to D3, D4, D17, D36, D41, D42)
- **Date:** 2026-07-30
- **Status:** Active

## Decision
**Where work items live is now pluggable, selected per-project by a new `AIND_TRACKER=ado|file` (default `ado`) — a script-only change behind a tracker-adapter layer (`scripts/aind-tracker.sh`), mirroring the D36 forge adapter; `commands/`, `skills/`, and `agents/` are essentially unchanged.** The flow hangs off a "work item" for six operations — read the story, drive its AIND status, post signed comments, resolve dependencies, link the PR, and attach usage telemetry — all previously hardwired to ADO Boards across ~6 scripts. Those are extracted into one set of tracker-agnostic verbs (`tracker_fetch`, `tracker_get_state`/`tracker_set_state`, `tracker_comment`, `tracker_deps`, `tracker_attach`/`tracker_field_accumulate`, `tracker_link_pr`, `tracker_url`, `tracker_new`) that dispatch on `AIND_TRACKER` to a `_ado_*` implementation (today's logic, moved verbatim from `aind-status.sh`/`aind-comment.sh`/`aind-deps.sh`/`aind-workitem.sh`/`aind-usage.sh`) or a new `_file_*` implementation. The existing scripts become thin callers; `aind-links.sh`'s hardcoded work-item URL becomes `tracker_url`, and `aind-usage.sh`'s write side becomes `tracker_attach`/`tracker_field_accumulate` (the token *collection* from agent-host logs is tracker-independent and untouched).

**The `file` backend is one markdown file per work item** (`<AIND_TRACKER_DIR>/<id>.md`), at a **configurable path defaulting to `<main-checkout>/.aind/items`** that **may live anywhere, including outside the repo** — the case that motivated this (a project with **no ADO backlog / code-only PAT access**). Two requirements shaped it, and **the no-deadlock requirement is what rules out a single CSV/Excel source of truth**: Excel takes an exclusive OS lock while open (the plugin literally cannot write — the exact deadlock), and any single shared file serialises every write and clobbers concurrent human edits. File-per-item makes items independent (acting on 42 never contends with a human editing 43); each file splits a **machine-owned YAML front-matter block** (only the adapter rewrites it — flat scalars `id`/`title`/`state`/`dependsOn`/`links`/`attachments`/`durationSeconds`, so no YAML parser is needed) from **human-owned `##` sections** (`Description`/`Acceptance Criteria` the adapter only *reads*; `Comments` it only *appends* to — it never edits prose); and **every write is temp-file-then-atomic-`mv`**, so the adapter never holds a file open and can write even while the file is open in an editor (no locks → nothing to deadlock). The default dir is rooted at the **main checkout** (via `git --git-common-dir`), not `$PWD`, so it is stable when a phase has cd'd into a worktree (the same trap D42 hit).

**The file backend is genuinely simpler than ADO, not just parity:** a scalar `state:` field is inherently single-valued, so the D3/D4 single-tag invariant (read→normalise→REST-`replace`→verify→auto-correct) and the D43 native-State mirror collapse to one field write; comments are appended as markdown with a real `<!-- AIND-AGENT: <name> -->` marker (no `md_to_html`, no `display:none` span — the D3 HTML-strip constraint is ADO-only); dependencies are a `dependsOn:` list rather than parsed relation URLs; telemetry blobs are files under `attachments/` with time in `durationSeconds`; `tracker_new` scaffolds from a shipped `project-template/item-template.md` assigning `max(existing)+1` (ADO items are still made in the ADO UI — `_ado_new` declines with guidance), and a warm human-facing command **`/aind:new-item`** wraps it with a short guided Q&A that drafts the Description/Acceptance/dependencies into the file for the human to review before running intake (file-tracker only, gated like `/aind:map-states` is to ADO). Numeric ids are preserved on both backends so the `AB#<id>` / `AIND-LINKS` (D17) PR join is unchanged. `tracker_link_pr` records the PR URL in the item's `links:` for the file backend and is a **no-op on ADO** (which links natively at create time via the forge's `az repos pr work-item add`, or the Boards↔GitHub app) — the forge call is left in place to avoid churning the live-validated ADO path. The **telemetry verbs are best-effort** (a die inside them is contained in a `( … )` subshell so a failure warns and returns non-zero instead of aborting a phase), matching the D42 discipline; the status/comment verbs stay fatal.

**Config + wiring:** `aind-common.sh` maps `.tracker`→`AIND_TRACKER` and `.trackerDir`→`AIND_TRACKER_DIR`, and its "already configured" short-circuit is generalised from `AIND_ADO_ORG` alone to *either* sentinel (so the file backend, which sets no ADO org, still loads). `aind-preflight.sh` gains a `file` branch (item-dir writable + `jq`; gitignore check only when the dir resolves inside the repo) and makes az/PAT/`azure-devops`-extension checks conditional on *either* the tracker *or* the code host being ADO. `/aind:onboard` and `/aind:kickstart` drop the "work items always live in ADO" assertion and **elicit the tracker** (suggest-don't-assert per D18/D31 — default-highlight `file` when the code host isn't ADO), then write `.tracker`/`.trackerDir`, seed the template, add the `.aind/items/` gitignore line **only** for the in-repo default (an external path is never gitignored), and gate the PAT step + native-State mirror on the ADO tracker. `/aind:map-states` short-circuits under the file tracker. The `aind-workitem`/`aind-status`/`aind-comment` skills are genericised (their `description` frontmatter drives discovery); `aind-workitem` now emits **normalised JSON** (`{id,title,description,acceptanceCriteria,state,dependsOn[],links[]}`) both backends produce.

**Signing enforcement** for the file backend holds by **routing** (every comment goes through `tracker_comment`, which signs) rather than the ADO PreToolUse URL hook, which has no file-write analogue; a file-write-interception hook is possible later but not built (a raw file edit bypassing signing is low-risk and hard to intercept generally). Config side of the D1–D15 line: the status model (D4), gates, plan-PR/assumption-thread contract (D5/D10), and artifact-linking contract (D17) are untouched — only *where* a work item lives changes.

## Rationale
The tracker is a **third orthogonal axis** alongside D22's agent host (Claude/Copilot) and D36's code host (GitHub/ADO Repos), and it had never been abstracted. The forge adapter (D36) is the proven template — one dispatch file, opaque canonical vocabulary, thin callers, zero changes above the script line — so reusing that shape is the cheapest correct move and keeps the intake/planner/coder/reviewer prompts unchanged. The user's real scenario (code-only PAT access, no board) made ADO a hard blocker for an otherwise host-neutral flow, so a backend that needs *nothing but a directory* removes it. **Markdown-file-per-item was chosen over CSV/Excel because it is the only option that satisfies both stated requirements at once** — user-friendly to create/edit *and* free of the write-contention deadlock — and the machine/human region split plus atomic writes make "no deadlock" a structural property rather than a hope. Storing the default at the main-checkout root (not `$PWD`) pre-empts the worktree drift D42 already paid for. Keeping `AIND_TRACKER=ado` the default and making the file path configurable-with-an-in-repo-default means existing projects are byte-for-byte unaffected (the D36/D37 regression bar) while the new case is one setting away. The file backend deleting the single-tag dance and the HTML-carrier contortions is a real simplification that only surfaced once the tracker was abstracted — evidence the abstraction sits at the right seam. Leaving the ADO PR→item link in the forge (rather than fully relocating it into `tracker_link_pr`) trades a small axis-purity blemish for not disturbing a live-validated path; full relocation is a later cleanup. A CSV/Excel *view* (export/import) on top of the file store was explicitly deferred — the markdown files are the source of truth, and a spreadsheet can be a disposable, regenerable view later if bulk editing ever hurts. Nothing here touches the flow, so it sits on the config/packaging side of the D1–D15 line, exactly like D36 (code host) and D41 (config streamlining).
