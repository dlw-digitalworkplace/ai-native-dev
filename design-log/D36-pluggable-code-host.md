# D36 — Pluggable code host — Azure DevOps Repos as an alternative to GitHub

- **Area:** Pluggable code host — Azure DevOps Repos as an alternative to GitHub (cross-cutting; packaging, config side of the D1–D15 line)
- **Date:** 2026-07-13
- **Status:** Active

## Decision
**The code, its pull requests, and its PR comments can live in either GitHub _or_ Azure DevOps Repos, selected per-project by a new `AIND_CODE_HOST=github|ado` (default `github`) plus `AIND_ADO_REPO` — a script-only change behind a forge-adapter layer; `commands/`, `skills/`, and `agents/` are unchanged.** **Key realisation: git is already host-neutral** (ADO Repos is plain git), so every `git` operation the flow performs — branch/checkout/push/fetch in the PR-openers, all of `aind-complete.sh`'s cleanup, and the orphan-branch lessons plumbing (D30) — works against an ADO remote unmodified. The GitHub coupling is concentrated in **one layer**: the `gh` CLI calls and GraphQL review-thread mutations. That layer is extracted into a new **`scripts/aind-forge.sh`** exposing host-agnostic verbs (`forge_pr_create`, `forge_pr_list`, `forge_pr_view`, `forge_pr_diff`, `forge_comment`, `forge_thread`, `forge_resolve`, `forge_reply`) that dispatch on `AIND_CODE_HOST` to a `_gh_*` implementation (today's code, extracted verbatim) or a new `_ado_*` implementation built on **`az repos pr` + the ADO PR Threads REST API**, reusing the **`AZURE_DEVOPS_EXT_PAT` already present** (no new credential). The existing PR scripts (`aind-open-plan-pr.sh`, `aind-open-code-pr.sh`, `aind-review-pr.sh`, `aind-thread.sh`, `aind-revise-plan-pr.sh`, `aind-revise-code-pr.sh`, `aind-complete.sh`, `aind-common.sh`'s `aind_find_code_prs`, and the dreamer's config-PR opener in `aind-dream.sh`) become thin wrappers over these verbs. **The `digest`/`thread=<id>` tokens stay opaque** so the reviewer/coder prompts never learn which host they run on (the adapter hides whether a token is a GitHub GraphQL node id or an ADO `threadId:commentId`). **Signing (D29) becomes host-aware:** `aind_gh_signature` is generalised to `aind_pr_signature` and emits the machine marker in a carrier the host preserves. **Native work-item↔PR linking is *simpler* on ADO** — same platform, so `az repos pr create --work-items <id>` hard-links it (no Azure Boards GitHub app needed); `AB#<id>` in the title stays a human-readable marker. **Three open questions are deliberately settled by _live validation during the build_, not up front** (matching the plugin's "trust a live run over docs" ethos, D22): **(1)** whether ADO PR markdown preserves HTML comments — decides both the D29 signature marker *and* the whole `AIND-LINKS` block (D17), which are HTML comments; if ADO strips them (as it does in work-item fields, hence D3's `display:none` span), the ADO carrier switches to a span or fenced marker; **(2)** ADO inline-anchoring semantics (`threadContext.filePath` + `rightFileStart` line/offset vs. GitHub's `commit_id`+`path`+`line`+`side`); **(3)** the thread-status mapping (ADO's `active/fixed/closed` enum vs. GitHub's boolean `isResolved`) the "resolve before merge" gate (D5) depends on. `aind-preflight.sh` gains host-conditional checks (`gh`+auth for github; the `az repos` extension + PAT Code scope for ado); `/aind:onboard` (D18) and `/aind:kickstart` (D31) ask which code host and write `AIND_CODE_HOST`; `design-doc.md`'s GitHub-specific prose is reframed to "code-host PR". **Terminology guard: this "code host / forge" axis is DISTINCT from D22's "second host" (Claude Code vs GitHub Copilot CLI, the _agent_ host)** — two orthogonal axes, four combinations; the docs must not conflate "dual-host". Config side of the D1–D15 line: the status model (D4), gates, plan-PR/assumption-thread contract (D5/D10), and artifact-linking contract (D17) are untouched — only the mechanics of *where* a PR lives change.

## Rationale
Supporting ADO code hosting looked like it might fork the flow; tracing the coupling end-to-end showed it does not, because **git is the same on both hosts** and AIND already routes every mechanic through scripts ("commands are thin; what can be scripted is scripted") — so the entire divergence collapses to one adapter and zero changes above the script line, which is the cheapest possible shape and preserves the reviewer/coder/planner prompts exactly. A forge-verb interface (over per-script `case $host` branches) localises the two implementations in one file, keeps the PR scripts readable, and makes the opaque-token discipline enforceable in one place. Reusing the existing ADO PAT means no new identity or secret story (unlike the still-deferred service identity, D6/Q7). Keeping the three render/anchoring/status questions as *live spikes* rather than pre-deciding them follows the same empirical rule that repeatedly corrected stale docs on the Copilot port (D22): the HTML-comment behaviour in particular is cheap to test and load-bearing for two separate features, so it is de-risked first in the build, not guessed now. Native ADO work-item linking being *easier* than the GitHub path (same platform, a first-class `--work-items` flag) is a genuine simplification, not just parity — it strengthens D17's canonical-pointer layer on the ADO side. Naming the axis distinctly from D22 is a deliberate guard: "host" already means the agent runtime in this repo, and letting it also mean the code forge would make every "dual-host" statement ambiguous. Nothing here touches the flow, so it sits cleanly on the config/packaging side of the D1–D15 line, exactly like the Copilot second-host work (D22) and the standards-plugin split (D25).
