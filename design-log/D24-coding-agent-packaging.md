# D24 — Build phase — coding agent packaging & first-iteration scope

- **Area:** Build phase — coding agent packaging & first-iteration scope (build phase, follows D7)
- **Date:** 2026-06-30
- **Status:** Active

## Decision
**The coding agent is a warm in-session slash command `/aind:implement <work-item-id>` — not a subagent** (consistent with D20: cold = independent verification only; warm command = human-facing authoring). It authors code that a human and the future cold reviewer check, so it has nothing hot to stay independent *from*. **Single coder, not per-domain:** per-task conventions arrive through each task's cited `rules/*.md` (D23); per-domain splitting stays parked (D7). **Polish (D7) is the final in-context phase of the same command** — warm, shares the coder's context, applies cited-rule style/formatting/self-consistency tweaks only (no structural or behavioral change), then opens the code PR. **Grounding (D17):** ID → resolve the merged plan (`AIND-LINKS` block / the `plans/<id>/plan.md` convention) → read the plan + each task's cited `rules/*.md` + the project's build/run **skills**; build/run mechanics stay **project skills** (D18), never plugin scripts — the plugin adds only the GitHub-flow twin of the plan-PR opener (`aind-open-code-pr.sh`: push branch, `gh pr create`, write the code PR's `AIND-LINKS` block incl. the plan-PR URL, native-link to the work item). **Code-branch naming:** the coder **generates** the branch from a fixed convention **`[type]/<work-item-id>-<short-name>`** (e.g. `feat/123-new-component`, `fix/456-typo`); this does not break D17 — nothing in the *flow* constructs or recognises a branch by name, the agent picks it once and every later agent still reaches the branch *through the code PR*. **State (D4):** `Ready for implementation` → set `In implementation` at start; the code PR owns all fine iteration (no tag movement). **Stuck-state (D12):** cap retries → stop → `Needs attention` → post the trail; a merge conflict gets one automated rebase attempt, then escalates. **First-iteration scope ends at code-PR creation:** all test authoring is deferred (neither the cold test-writer D8 nor the coder's own warm unit tests D7/D8 — D8/D9 stay the target), and code review (cold reviewer, D7 Phase 4), the human merge gate, and the terminal `Implementation complete` write (`/aind:complete`, D13) are explicitly the *next* iterations, not this one.

## Rationale
Packaging follows the warm/cold line D20 finally drew: the coder authors and a human / the cold reviewer verify, so coldness buys it nothing while re-incurring the D19 friction D20 paid to remove (fresh-context permission re-prompts, command→Task indirection, cold re-grounding cost); a command is also the proven headless handle (D6, `claude -p`). One coder honors D7's "modelled as one; split is project-specific" and leans on D23's rule-cited tasks for per-domain conventions, so domain-awareness needs no extra agents. Polish stays warm and in-context because that is the one place warmth is load-bearing (D7) — re-grounding it cold would redo the coder's reading for zero independence gain. Dev skills staying project-side preserves portability (no project values in the plugin) and reuses what onboarding already stubs (D18); the plugin only mirrors the plan-PR opener for the code PR. Fixing the branch convention *in the agent* (not in a flow script) keeps D17's contract intact — the PR remains the only handle — while giving humans a readable branch. Deferring all testing and stopping at PR creation makes this iteration a single reviewable surface (the "name what's actually available now" discipline of D15), with review / merge / complete added as clean follow-ons rather than half-built now.
