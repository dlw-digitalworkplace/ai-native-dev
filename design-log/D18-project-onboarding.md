# D18 — Project onboarding

- **Area:** Project onboarding (one-time, pre-flow; bootstraps the config layer)
- **Date:** 2026-06-25
- **Status:** Active

## Decision
**A human-invoked onboarding agent (`/onboard`) bootstraps a project's `.claude/` config from its existing codebase, as the day-one mirror of the dreamer (D16).** It reads the repo, **discovers the rule areas it actually needs through three lenses** — **technical layers** present (front-end, back-end, web-jobs, infra, …), **cross-cutting concerns** with a notable/non-standard approach (e.g. a custom pin-code auth scheme), and the **functional/domain architecture** (the product's core concepts and invariants, e.g. "app-of-mini-apps; every entity scoped to a couple of IDs") — and **drafts** the initial config: one `rules/<area>.md` per discovered area, a `CLAUDE.md` that imports exactly those files via the root-import model, **project-specific skills** stubbed from the real build/test/run commands it finds (manifests, CI), and a copy of the seed intake rubric (D11). **Refinement (2026-06-25):** the layer names are *examples, not a fixed list*, and discovery is **strictly evidence-only** — a rule file is created only for an area that genuinely exists (no test framework → no testing rule; no docs system → no docs rule), and the three-lens prompt was added so onboarding does not stop at technical layers but also surfaces cross-cutting concerns and the functional/domain architecture. The shipped `project-template/rules/` is a single category guide (`_TEMPLATE.md`), not a set of stub files, so nothing biases the agent toward a specific domain set. It then runs a **preflight probe** and reports the remaining setup prerequisites (PAT, gh access, jq, the Boards↔GitHub integration, branch protection). **Authority & gate:** it **suggests, the human decides** (the D2 pattern) — every generated file is a clearly-marked **DRAFT** for review, and it is **bounded to the config layer, never the flow** (the same D1–D15 boundary the dreamer respects, D16). **Delivery:** draft files written directly into `.claude/` (reversible via git, reviewed before commit) — **not** a PR-against-`.claude`, because the PR-review machinery (D16's one-cycle-one-PR) presupposes a running flow and a configured repo that do not yet exist at onboarding.

## Rationale
Adopting AIND on an existing repo otherwise starts from empty template stubs a team fills by hand; turning the codebase itself into the first draft of its rules is faster and more grounded. Reusing the agent-suggests/human-decides gate (D2) avoids inventing a new trust model, and keeping the onboarder on the config side of the D1–D15 line is the same failure-class avoidance as the dreamer — a setup agent that could rewrite the flow is exactly what that boundary designs out. Draft-files-not-PR is the right call *specifically at onboarding*: the human gate is preserved (review before commit) without the bootstrap chicken-and-egg of needing the flow configured to review its own configuration. Discovering domains rather than fixing them keeps the rule split honest to each repo's real shape, and the root-CLAUDE import model (chosen for project rules) wires in exactly the domains found. Folding the preflight probe into onboarding means the team finishes the command knowing precisely what remains to set up. The onboarder/dreamer symmetry is deliberate: **onboarding bootstraps the config from the codebase, dreaming evolves it from the flow's exhaust** — two ends of the same agent-config-improvement axis, both proposing, both human-gated, both barred from the flow.
