# D39 — Parallel work — shared directories across worktrees

- **Area:** Parallel work — shared directories across worktrees (config/packaging side of the D1–D15 line; extends D37)
- **Date:** 2026-07-22
- **Status:** Active

## Decision
**A worktree-enabled project can now share heavyweight, gitignored directories (chiefly `node_modules`) across its per-phase worktrees instead of re-populating them per tree, via a new optional `symlinkDirs` list in `.claude/aind-worktree.config.json`.** This builds the extension D37 named-not-built. Each entry is a repo-relative directory that, on `aind-worktree.sh ensure`, is **linked** from the worktree to the *same* directory in the main checkout — a **directory junction** on Windows (`cmd /c mklink /J`, no admin and no Developer Mode, unlike a `mklink /D` symlink; same-volume only, which holds because worktrees live under the repo) and a plain `ln -s` on Unix/CI. A missing target in the main checkout is created empty and warned (so a later install-from-worktree, which writes *through* the junction into the shared store, populates it). **The load-bearing correctness point is teardown:** the existing `copyFiles` teardown does `rm -rf`, which through a junction would delete the *real* shared directory in the main checkout — so `symlinkDirs` gets its **own** unlink step that runs **before** the `copyFiles` delete and before `git worktree remove` (in both `remove` and `prune`), and it removes only the **link** (`cmd /c rmdir` on Windows removes a junction without following it; `rm` the symlink on Unix), **never `rm -rf`**. The link step is iterated from the config list, not from filesystem probing (junctions are unreliable to detect via `test -L` on MSYS). **The trade-off is explicit and documented, not hidden:** a shared `node_modules` is genuinely shared state — a branch that changes dependencies needs an install that mutates the shared store (there is no per-branch isolation), and a concurrent install in one worktree can disturb a build in another. So the docs **recommend pnpm** (global content-addressable store → hardlinked, dep-isolated, near-instant per-tree installs with true isolation) as the correct answer for greenfield/adoptable projects, and offer `symlinkDirs` as the portable mechanic for npm/yarn projects that cannot switch. Generic (a `symlinkDirs` *list*, mirroring `copyFiles`) over a node-specific flag, so it also covers `.next/cache`, a Python `.venv`, build caches, etc. **Strict no-op when `symlinkDirs` is absent or empty** (regression bar, same as the whole worktree feature being a no-op without its config file). Script-only change plus docs: `aind-worktree.sh` (`ensure`/`remove`/`prune`), `aind-preflight.sh` (reports configured shared dirs; warns on a not-yet-present target), the sample config, and the README/GETTING-STARTED/project-template parallel-work sections. Windows path-conversion is disarmed with `MSYS_NO_PATHCONV=1` around the `cmd` calls (same family as the leading-slash-argv and CRLF gotchas already handled). **Distinct from D22's agent-host axis and D36's code-host axis** — same working-tree-layout axis as D37; the flow, status model, gates, and forge are untouched.

## Rationale
Sharing large dirs was the one piece D37 deferred, and front-end (`node_modules`) is exactly where re-installing per worktree hurts, so the parallelism D37 unlocked is only fully useful once the heavy dir can be shared. Junctions (over symlinks) are the Windows-correct primitive because they need no elevation and node_modules is same-volume by construction; keeping the mechanic in portable bash (junction on Windows, `ln -s` elsewhere) preserves the D22 dual-host + future-CI story rather than leaning on any host's native worktree-symlink feature. Making the unlink its own pre-teardown step is not optional polish — a `rm -rf` through a live junction is a data-loss bug against the developer's real `node_modules`, so the safe primitive (`rmdir` / `rm` the link only) and the strict ordering are the core of the decision. Recommending pnpm as the first-class answer and `symlinkDirs` as the fallback matches the honest trade-off the user accepted: sharing buys speed/disk at the cost of per-branch dependency isolation and a concurrent-install hazard, whereas pnpm buys both — so the docs must not present the shared junction as free. Generic-over-specific matches the existing `copyFiles` shape and avoids a second, narrower config idiom for the same "seed a worktree with something git won't" need.
