# D52 — Create work items in Azure DevOps from `/aind:new-item` (amends D46)

- **Area:** Work-item creation on the ADO tracker (config/packaging side of the D1–D15 line; amends D46; relates to D3, D4, D43)
- **Date:** 2026-08-06
- **Status:** Active

## Decision
**`/aind:new-item` now creates a story directly in Azure DevOps Boards under the ADO tracker, at full parity with the file backend — reversing D46's stub, which declined ADO creation and told the human to author the story in the Boards UI first.** D46 shipped `tracker_new` for the file backend only (`_ado_new` was an `aind_die` with guidance); the command guarded itself to `file` and refused to run under `ado`. The gap this closed: on the ADO tracker there was no in-flow way to author a story — the human context-switched to the Boards web UI, hand-set nothing AIND-specific, and came back to run intake. The two backends now behave the same: one guided Q&A drafts a story that is left for human review before the flow starts.

**`_ado_new` (in `aind-tracker.sh`)** takes `"<title>" [--deps "<id>,<id>"]` and reads the **description + acceptance criteria on stdin**, split on a line reading exactly `---AIND-AC---` (description before it, acceptance criteria after) — so `/aind:new-item` feeds both rich-text fields in **one heredoc** attached to the D49 resolver's outer `bash -c`, with no shell-escaping of the story prose (the same single-command / heredoc discipline the signed-comment path uses; a pipeline would re-prompt for permission). It builds a JSON-Patch (`System.Title`, `System.Description`, `Microsoft.VSTS.Common.AcceptanceCriteria`, and a `System.LinkTypes.Dependency-Reverse` relation per `--deps` id), POSTs it to `…/_apis/wit/workitems/$<type>` via the existing `_ado_api` helper, then reuses **`_ado_set_state <id> "Ready for intake"`** to stamp the initial status — so the single-`AIND status`-tag invariant (D3/D4) and the native-State mirror (D43) come for free rather than being re-implemented. It echoes `<id> <url>`, mirroring the file backend's `<id> <path>`. Description/acceptance markdown is run through the existing `_ado_md_to_html` (ADO's fields are HTML rich-text), and — as in `_ado_attach` — the `/fields/…` and `/relations/-` JSON-Patch paths are built **inside jq**, never as a shell argument, so MSYS can't rewrite a leading slash into a Windows path.

**The work-item type is configurable** via a new optional `.ado.workItemType` → `AIND_ADO_WORKITEM_TYPE` setting (default **`User Story`**), so projects whose process template names the type differently (`Product Backlog Item`, `Issue`, …) can create the right type. **`/aind:new-item`** loses its file-only guard: it detects the backend (`aind-tracker.sh kind`) and branches — the file path is unchanged (scaffold → `Read`/`Edit` the file → hand back the path), the ADO path creates the populated story and hands back the **ADO URL** for review in the web UI (there is no local file to edit, so the ADO branch skips the fill-in step).

## Rationale
This is a small, contained completion of D46, not a new axis: D46 built the tracker-agnostic `tracker_new` verb and only stubbed the ADO side because the motivating scenario was the *file* backend (no board at all). For teams that *do* run on ADO Boards, the stub forced a context switch out of the flow to author every story — friction with no upside, since the guided Q&A is backend-agnostic and the create is a single REST call over plumbing that already exists (`_ado_api`, `_ado_md_to_html`, `_ado_set_state`, the `@uri` type-encoding pattern from `aind-states.sh`). Layering the status stamp on top of `_ado_set_state` (rather than setting `System.Tags` in the create patch) keeps exactly one place responsible for the one-tag invariant and the D43 mirror. The stdin-marker convention was chosen over `--desc`/`--ac` positional prose or temp files because a heredoc on the resolver command carries multi-line prose with apostrophes/quotes verbatim and stays inside a single allowlisted `bash -c` (no re-prompting), while explicit `--desc <file>`/`--ac <file>` flags remain accepted for scripting and offline tests. Creating the item still ends at a **draft awaiting the human** (suggest-don't-assert, D2/D18): the command never runs intake or sets any status beyond `Ready for intake`. Config side of the D1–D15 line — the flow, status model, gates, and PR contract are untouched; only *how a story is born* on the ADO tracker changes.

## Status / validation
Offline-validated: `_ado_new` exercised end-to-end with a mocked `_ado_api`/`_ado_set_state` — the JSON-Patch body is correct for (a) description + acceptance + multiple deps, (b) title only, and (c) description-without-marker; the `---AIND-AC---` split, the `$`-prefixed URL-encoded type, and the Dependency-Reverse relation URLs all build as expected; the file backend's `new` (including a harmless stray `--deps` flag) is a strict no-op regression; `bash -n` clean; `claude plugin validate` passes (the one accepted root-`CLAUDE.md` warning).

**Live-validated** against a real ADO-tracker project (Scrum process): a create landed a real Product Backlog Item with the title, HTML description, HTML acceptance-criteria list, and the single `AIND status - Ready for intake` tag all correct (then cleaned up). **The default work-item type is a live gotcha:** the default `User Story` only exists in the **Agile** process — a Scrum project has `Product Backlog Item`, a Basic project has `Issue` — so a create there fails with ADO `VS402323: Work item type … does not exist`, which is exactly why the type is a per-project setting. The failure surfaced *only* because it was run directly; through the command, an agent had "helpfully" fallen back to hand-drafting the story for manual paste into the Boards UI and swallowed the error. `commands/new-item.md` now instructs the ADO path to **surface a create failure verbatim** (and point at `ado.workItemType`) rather than fall back to a manual-entry draft. **Next: a full `/aind:new-item` → `/aind:intake <id>` run through the command** once the type is configured, to confirm the command path (not just the script) behaves.
