# D6 — Triggers / execution

- **Area:** Triggers / execution (cross-cutting)
- **Date:** 2026-06-17 (amended 2026-06-24)
- **Status:** Active

## Decision
**Execution matures in stages, all sharing one `.claude` config and the same agent definitions — only the trigger and identity change.** **v0 (local):** run each handoff from the Claude Code CLI (`/intake`, `/plan`, or `claude -p`) on a developer machine, acting as the developer's own ADO/GitHub credentials — no service identity, no CI — to prove the agents before any infra; plan-review revisions are re-run by hand. **v1 (GitHub Actions):** agents run via the official `claude-code-action`, kicked off by `workflow_dispatch` (human passes the work-item ID); plan-review revisions are event-driven via PR / `@claude` events (status unchanged); agents read/write ADO via a service identity; no service hooks, orchestrator, or staleness sweep. **v2 (pre-unlocked — service-hook admin confirmed):** swap the manual `workflow_dispatch` for an ADO **service hook → GitHub `repository_dispatch`** keyed on tag transitions (`Ready for intake` → intake; `Intake approved` → planner), plus a scheduled staleness sweep — same workflows, tag-driven. **The build phase (D7) extends the same model unchanged:** v1 `workflow_dispatch` kicks the coder (implement → polish → open PR) and the reviewer is PR-event-driven exactly like plan review; v2 keys the coder off the `Ready for implementation` → build transition. **AMENDMENT (2026-06-24): near-term scope is manual execution only.** The staged target above stands as the intended trajectory, but the *current* scope is deliberately narrowed to **manually-run execution** — i.e. v0 (local CLI, developer's own credentials) is the working mode for now. **v1's unattended-automation aspects are descoped:** the service-identity decision (single bot vs. per-agent, PAT vs. Entra SP, secret storage) is explicitly **out of current scope** and the question that covered it (formerly Q7) is **closed by descoping** — to be reopened when GitHub Actions automation is actually picked up. v2 (event-driven service hooks) is likewise future work. Nothing about the agent definitions, the flow, or the state model changes; only the automation/identity layer is shelved.

## Rationale
Local CLI is the lowest-setup way to validate the agents first; human-triggered GitHub Actions is the cheapest shared path (zero bridge infra), and the genuinely GitHub-native part — plan-PR iteration — gets real automation for free. Because every mode shares one config, promotion is zero change to agent logic; only trigger + identity move. Tags stay the state record throughout (D4), so v2 keys off them with no rework. Claude Code is first-party on GitHub Actions; ADO has no first-party task. **On the amendment:** scoping to manual execution removes the only thing that needed a service identity (an unattended agent), so the identity/secrets question stops being a prerequisite and can be parked without blocking progress — proving the agents by hand is the priority, and the automation layer is a clean later addition that touches trigger + identity only.
