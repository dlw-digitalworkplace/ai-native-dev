# D9 — Testing — live / E2E

- **Area:** Testing — live / E2E (point 2 of 2)
- **Date:** 2026-06-24
- **Status:** Superseded by D33

## Decision
**(SUPERSEDED by D33, 2026-07-09 — the live/E2E agent is removed as a first-class actor; live verification survives only as an optional Definition-of-done line satisfied by a human PR signal. Retained for history.)** **Optional, pre-merge, blocking live/end-to-end gate in the build phase, on the code PR.** **Where:** pre-merge and blocking — runs on the code PR alongside CI and the reviewer; a failure blocks merge and routes back to the coder like any other failing gate. Stays at the same altitude as the rest of the build gates, so the terminal state is unchanged (`Implementation complete`) and nothing spills into the (still out-of-scope) deployment phase. **Trigger:** **planner-gated, exactly like D8** — the plan recommends whether the story warrants live testing; the human ratifies at plan review. A story now carries **two orthogonal test recommendations** (spec-level D8, live D9): either, both, or neither. **Who:** a **cold E2E agent** — same re-grounding contract as the test-writer (D8) and reviewer (D7): separate invocation, artifacts only, never the coder's context — authors and runs **user-visible behavioral scenarios** against the ACs (the full-stack altitude of D8's pattern). **Project escape hatches (by design):** the *how-to-run-the-app* mechanics are left to each repo because they are inherently per-app. A project may (a) implement automated E2E the cold agent drives, or (b) **skip the agent and have a developer run the app locally and test manually**, signalling the pass in the PR like any other human input. The design mandates *that the gate is cleared when the plan calls for it*, not how. **Status & CI:** no new status — the gate lives inside `In implementation` (coarse/fine split, D4), and a manual pass is just a human PR signal (no new machinery). The gate is "live testing happened," **not** "the CI E2E job is green": on the manual path there is no CI E2E job at all.

## Rationale
A blocking gate is the only version that is a real gate; advisory E2E that is often red gets ignored. Post-merge E2E would push the first live check past the terminal state into deployment territory that isn't designed yet, and would need a revert story — pre-merge keeps the gate honest and self-contained. Forcing a *running app* into every PR is exactly the per-app complexity worth refusing to pin down centrally, so the two escape hatches (automate it, or a human runs it locally) let each project choose its cost. Cold + behavioral + planner-gated keeps point 1 and point 2 a single coherent pattern — cold behavioral testing at two altitudes (unit-ish in D8, full-stack here) — rather than two unrelated bolt-ons. Signalling a manual pass in the PR reuses the existing human-in-PR pattern instead of inventing a manual-test checkpoint.
