# D55 — Local same-branch flow (`flow.mode: local`) — plan + code on one branch, plan reviewed in the working tree

- **Area:** The flow's gate placement (amends D1/D5/D10/D13/D7 behind an opt-in toggle); touches `commands/plan.md`, `commands/approve-plan.md`, `commands/implement.md`, `scripts/aind-open-code-pr.sh`, `scripts/aind-common.sh`, a new `scripts/aind-flowmode.sh`, and the config/docs surfaces
- **Date:** 2026-09-16
- **Status:** Active — offline-validated; live-validation pending

## Decision
**An opt-in `flow.mode: "local"` runs the plan and the implementation on ONE story branch, with the plan reviewed in the working tree (e.g. VS Code) instead of a plan PR. Only the *plan* PR is removed: the code still ends in a single code PR, so the cold reviewer, the review loop, and `/aind:complete`'s merge-then-tag are unchanged. The default `"pr"` flow is byte-identical to today.**

Concretely, when `flow.mode: local`:

- **One branch per story** — `<type>/<id>-<short-name>` (the existing code-branch convention). `/aind:plan` picks the name, creates the branch off the integration branch, commits `plans/<id>/plan.md` onto it, and **opens no PR / does not push** (new verb `aind-open-code-pr.sh start-local`, idempotent so a plan revision just re-commits). The session is left **on the story branch in the main checkout** so the developer reads the committed plan in their editor.
- **Plan gate = explicit confirmation.** With no plan PR there is no branch-protection "resolve every thread before merge" gate (D5). In the `local` flow `/aind:approve-plan <id>` **asks the human to confirm** (via `AskUserQuestion`) that they reviewed `plans/<id>/plan.md` before it sets `Ready for implementation`; it refuses on anything but an affirmative. It also **skips** the plan-branch cleanup (the branch lives on into build). *(An earlier design used a typed `--confirm` CLI flag; it was dropped — see the resolver note under Status.)*
- **Build continues on the same branch.** `/aind:implement` build mode **does not cut a fresh branch off integration**; it rediscovers the story branch by the `<type>/<id>-…` convention (new verb `resume-local`) and builds on it. At the end it opens **one code PR** whose diff carries plan.md + code. Revise mode is untouched — once the code PR exists, the branch is reached through it as always.
- **Single-tree, mutually exclusive with worktrees.** The whole point is that the developer sees the story branch in their own checkout, which is the opposite of the drive-from-main worktree model (D37) that keeps the session on integration. When `flow.mode: local`, the branch-owning scripts take the single-tree path unconditionally and `aind-flowmode.sh` warns if `worktree.enabled` is also set.
- **Mode resolution is config-only**, mirroring `.worktree.enabled` / `.tracker` / `.codeHost` (project-structural settings, not per-run choices): `.flow.mode → AIND_FLOW_MODE` mapped in `aind-common.sh`, resolved by `aind-flowmode.sh` (unknown → `pr`). Every command reads the same value, so plan/approve-plan/implement can't disagree. (A per-command override was considered and rejected: implement is single-token, and an arg-only override on `/aind:plan` would leave `/aind:implement` reading config and mismatching — the flow must be one consistent project property.)

The **status model is unchanged** — same nine tags (D53/D3/D4), same coarse/fine split, same transitions. Only *where* the plan-review and plan-approval gates live moves.

## Rationale
The two-PR flow is built for asynchronous, team-reviewed work. For a developer running the whole flow locally (D6's manual/local scope), routing a one-file plan through the GitHub/ADO PR UI is heavier than reading `plans/<id>/plan.md` in the editor — the friction the user asked to remove.

This is a **flow-level change (the D1–D15 line)**, not a config-layer feature: it re-opens gate placement (D1), the resolvable-thread plan gate (D5), the plan-PR shape (D10, which *rejects* same-branch by name), and the merge-then-tag transition trigger (D13). The "config layer vs flow" invariant bars the onboarder and the dreamer from touching any of these, so this ships as a **deliberate, human-authored decision**, opt-in and default-off, and **byte-identical when off** (the regression bar D37/D46 use).

It is framed within the design's own precedent for principled divergence from D10, **D14**: same-branch is acceptable when you *name what integrity is given up and how it is recovered*. Here:

- **What is given up:** D5's structural, un-skippable per-assumption checklist. In `pr` mode each open assumption is a resolvable thread that branch protection forces resolved-before-merge, so a silent merge is impossible by construction. Local review has no such infrastructural gate.
- **How it is compensated:** (1) `/aind:approve-plan` **prompts for an explicit confirmation** (`AskUserQuestion`) that the plan (and its *Assumptions & open questions* prose) was read; (2) the plan.md commit **rides in the code PR's diff**, so the cold reviewer still reads the assumptions (as prose, not per-item threads); (3) **attended** planning (D44) still resolves assumptions live via `AskUserQuestion`, so an assumption-heavy story loses nothing when run attended — the recommended combination. This is honestly a *weaker* gate than merge-blocking threads; it is an accepted trade for an opt-in local flow, documented as such.

The **branch handle** is the other named deviation. The framework's rule (D17 / the project CLAUDE.md operational rule) is "never reconstruct a branch name to find an artifact — reach it through the PR." In `local` mode there is no PR between `/aind:plan` and `/aind:implement`, so the story branch is rediscovered by the id-scoped `<type>/<id>-…` convention. This is **safe** because the join key is still the work-item id and the create-time convention is unique per item, and it is **scoped**: the moment the code PR is opened, the PR-as-handle rule resumes. It is sanctioned here explicitly rather than left as an implicit violation.

Two mechanics were made flow-aware in `aind-open-code-pr.sh open` and must stay defensive so the default flow is unchanged: the "has commits beyond integration" gate keeps the literal `git rev-list --count` on the `pr` path but uses a **plan-excluding** diff on the `local` path (so a branch carrying only plan.md is still rejected as "no implementation"); and the plan-PR-URL lookup for AIND-LINKS is skipped in `local` mode (there is no plan PR — the block already degrades to just the plan path).

**Rejected alternatives.** *Fully PR-less (local code merge too)* — loses the code-review gate, async team review, and the PR→lesson exhaust-capture (D30); the user chose to keep one code PR. *An in-file checkbox gate* (assumptions as `- [ ]` that approve-plan greps and blocks on) — a stronger structural substitute for D5, but the user chose the lighter explicit-confirmation attestation.

## Status / validation
Offline-validated (`bash -n` clean on the new/edited scripts; the repo runs no shellcheck):

- **`aind-flowmode.sh` resolution:** unset / `pr` / `local` / garbage → `pr` / `pr` / `local` / `pr`; uppercase + surrounding space tolerated (` LOCAL ` → `local`).
- **Local-flow verbs, throwaway repo (no live host):** `start-local` creates `feat/42-export`, commits `plans/42/plan.md`, opens no PR, leaves the tree on the story branch; a second `start-local` after editing the plan reuses the branch and re-commits (idempotent); an unchanged re-run reports "nothing to commit"; `resume-local` from `main` rediscovers and checks out the branch and prints its clean name; the `local` plan-excluding gate rejects a plan-only branch and allows one once code is added.
- **Byte-identical-when-off:** the `pr` path in `aind-open-code-pr.sh open` keeps the literal `rev-list` gate, the plan-PR lookup, and the worktree conditional (guarded `flow != local`, which is true by default); `AIND_FLOW_MODE` defaults to `pr` when the key is absent.

**Confirmation is a prompt, not a CLI flag — a fix from the first live run.** The initial design took a typed `--confirm` as a second CLI token, which made `/aind:approve-plan` the first command to pass a **two-token `$ARGUMENTS`** through the D49 resolver. A live run surfaced a corruption: the resolver depends on exact positional alignment of its two trailing args (`$1` = `${CLAUDE_PLUGIN_ROOT}`, `$2` = `$ARGUMENTS`), and when the plugin-root arg resolves **empty** (always, on Copilot — it's a Claude-only macro) and the host then **drops that empty arg or word-splits `$ARGUMENTS`**, the positionals shift and the resolver reads `--confirm` into the plugin-root slot (observed `R="--confirm"` → `[ -d "$R/scripts" ]` fails → self-locates to a stale `.copilot` snapshot). Reproduced offline: with the empty root arg dropped, `_ … "--confirm"` yields `R=[--confirm]`. The two-positional resolver `A="$1"; shift; ${A%% *}` (as used by `/aind:plan`, `/aind:complete`) carries the same latent fragility whenever its optional second token is actually passed. Fix: `/aind:approve-plan` is **single-positional again** (only the id flows through the resolver — the proven form), and the local-flow confirmation is obtained at the **agent layer via `AskUserQuestion`**, which can't corrupt the shell and is an un-skippable human gate all the same. (The `plan`/`complete` two-token resolvers are left as-is for now — noted as a latent risk to revisit.)

**Not verified:** any live GitHub/ADO run (plan → local review → confirm → build → single code PR → complete) with the AskUserQuestion gate; Copilot CLI; the interaction of a stale `worktree.enabled: true` alongside `flow.mode: local` beyond the warning. Live-validate end-to-end next on a real story.
