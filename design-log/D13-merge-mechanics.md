# D13 — Merge mechanics

- **Area:** Merge mechanics (build phase)
- **Date:** 2026-06-24
- **Status:** Active

## Decision
**In current (manual) scope, the merge is human-gated and a single CLI command performs the merge plus the terminal tag-write together.** **Merge trigger:** a person merges the code PR after the reviewer agent approves (or after the D7 human-verdict + final reviewer pass). This is committed as the design position for manual mode, not a stopgap — a human is the final authority on what lands. **Tag write:** the terminal `Implementation complete` tag is written by a **CLI command that also performs the merge** (folded into `/implement`'s final step, or a dedicated `/complete <work-item-id>`), acting as the **developer's own credentials** (the v0 model, D6) — no service identity. **Order and failure handling: merge FIRST, then write the tag.** If the tag-write fails after a successful merge, the item is left **recoverable** — it keeps `In implementation` and the human re-runs the tag step — and is *never* falsely marked complete; the reverse order is forbidden because a `Implementation complete` tag on an unmerged PR would make the state record lie (the discipline behind D4's single-tag invariant). **Explicitly deferred to the automation phase:** auto-merge-on-approval, and a PR-merge GitHub Action that writes the tag as the service identity — both presuppose the unattended machinery and service identity descoped under the D6 amendment (former Q7), so they wait until automation is picked up.

## Rationale
Manual scope (D6 amendment) removes the service identity that the original Q8 assumed, so the realistic answers collapse to human-gated + CLI. Doing merge and tag-write in one command keeps them from drifting — a merged PR with a stale `In implementation` tag is exactly the two-sources-of-truth failure D4 exists to prevent. Merge-first ordering makes the only possible failure a *recoverable, visibly-incomplete* item rather than a *false-complete* one: a lie in the state record is far worse than a missed update, since downstream readers trust the tag. Committing to human-gated (rather than holding it loosely) reflects that even once automation returns, a human merge gate is a defensible permanent choice; auto-merge is offered as a *future option*, not a planned default. Deferring the automation-mode answer keeps Q8 consistent with the Q7 descope instead of designing machinery that isn't in scope.
