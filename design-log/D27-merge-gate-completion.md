# D27 — Build phase — merge gate + terminal completion

- **Area:** Build phase — merge gate + terminal completion (Phase 4 close-out; realises D13)
- **Date:** 2026-07-01
- **Status:** Active

## Decision
**The build phase closes out with a human-run `/aind:complete <work-item-id> [pr-number]` — the build-phase twin of `/aind:approve-plan`.** It resolves the story's code PR, **verifies it is MERGED (refuses otherwise)**, writes the terminal `Implementation complete` tag, posts a signed completion note, and cleans up the merged code branch — in that order. **D13 realised as verify-then-tag, NOT command-merges:** the human merges the PR in GitHub (the human is the final authority on what lands), and `/aind:complete` *records* the result — it does **not** run `gh pr merge`. This still honors D13's committed safety invariant (the terminal tag is only ever written *after* a confirmed merge, so `Implementation complete` can never sit on an unmerged PR — the state-record lie D4 guards against; verify-then-tag satisfies "merge FIRST, then tag" trivially), and matches `/aind:approve-plan`'s confirm-merged→record shape exactly, keeping the command thin and free of merge-method/branch-protection surface. The residual drift D13's one-command-does-both was meant to prevent (a human merges but forgets to run `/aind:complete`) is the **same accepted gap already tolerated for `/aind:approve-plan`**, and D13 already defers the real close (auto-merge-on-approval + a merge Action) to the automation phase (D6). **PR discovery (the one new mechanic):** the code branch is coder-generated and non-derivable (D17), so `/aind:complete` *searches* the repo's PRs for the work-item id and filters to AIND's own markers — a title ending `(AB#<id>)` (produced by `aind-open-code-pr.sh open`) or an `AIND-LINKS work-item:` URL ending `/edit/<id>` — requiring **exactly one MERGED match**; it **refuses** on none-merged ("merge it first"), no-match, or ambiguity, and takes an optional explicit **`[pr-number]`** override so it never *guesses* which PR (suggest-don't-assert). **No hard reviewer-approval gate:** there is no "reviewer approved" tag (the tag stays `In implementation` through the review loop), so the **merge itself is the human's act of acceptance** — mirroring how `/aind:approve-plan` trusts that the human merged only after resolving threads. **Order + recoverability (D13):** verify → `aind-status.sh "Implementation complete"` → signed `coder` completion note → branch cleanup **last**; nothing mutates before the merge is confirmed, so a tag-write failure leaves the item *recoverable* (`In implementation`), never false-complete, and a cleanup hiccup can never corrupt status. **Branch cleanup tuned for auto-delete-on-merge:** since GitHub usually auto-deletes the remote branch at merge, cleanup re-confirms MERGED then deletes the remote **only if still present** (no-op otherwise), **prunes** the stale `origin/<head-ref>` ref, and deletes the **local** branch (switching off it to the integration branch first, only when the working tree is clean; dirty → warn, leave it) — the local branch being what actually lingers from the `/aind:implement` run. **New mechanics:** `commands/complete.md` + `scripts/aind-complete.sh` (`verify`/`cleanup`). **Refinement (2026-07-01):** cleanup also leaves the developer on an up-to-date integration branch — after deleting the merged code branch, if the checkout ends up on the integration branch with a clean tree it **fast-forwards it to include the merge** (ff-only; a diverged local branch is left for a manual pull), so the local trunk isn't silently behind the just-merged work. **Scope: `/aind:complete` alone this iteration; the code-revision loop is deferred** (the twin of the plan-revision loop D21 — re-entering an already-open code PR to apply a wanted suggestion / a human tiebreak verdict / a touch-up, pushing to the same PR, optionally re-reviewing). Safe to defer because the common close-out path (CLEAN → human merges as-is → `/aind:complete`) needs no loop, and the suggestion/tiebreak sub-cases have a sanctioned interim bridge (a direct edit on the PR branch + push, then merge — a human decision at merge time). Still out: test-writer/E2E (D8/D9), dreaming (D16), automation (D6).

## Rationale
The realistic answers for manual scope collapse to human-gated + a thin CLI recorder, and `/aind:approve-plan` already proved that exact shape one phase earlier — reusing it (rather than D13's literal command-merges) keeps `/aind:complete` thin, avoids merge-method/branch-protection judgment the tool shouldn't own, and still guarantees D13's only load-bearing property: the terminal tag never precedes the merge. Verify-then-tag makes the *only* possible failure a recoverable, visibly-incomplete item, never a false-complete one — a lie in the state record is far worse than a missed update (the D4 discipline). Searching for the PR (vs. reconstructing a branch) is forced by D17's "reach the branch through the PR"; requiring a single MERGED match with an explicit override keeps discovery from ever guessing. Not gating on reviewer-approval respects that the merge *is* the human's acceptance (there is no approval tag to check) and mirrors the plan phase. Tuning cleanup for auto-delete-on-merge reflects the real post-merge state — remote gone, local branch lingering — so the command tidies what's actually left instead of erroring on an already-deleted remote. Shipping `/aind:complete` alone keeps a single reviewable surface (D15) and leaves the code-revision loop as a clean, well-scoped follow-on rather than a half-built bundle; the interim hand-edit bridge covers the only paths the loop's absence blocks.
