Config

Per-project config is two files under .claude/, both auto-loaded by walking up from the working directory (no source needed). /aind:onboard and /aind:kickstart create and fill them.

  • .claude/aind.settings.json — shared settings, checked in.
  • .claude/aind.env — secrets + per-user overrides, gitignored.

Every setting maps to an AIND_* environment variable, which is the interface the scripts read. Precedence: an already-set environment wins (so CI or a parent shell can override), then aind.env, then aind.settings.json fills any still-unset var.

worktree block (parallel work)

Opt in to AIND-owned git worktrees so one clone can drive several stories at once — implement one while planning the next. When on, /aind:plan and /aind:implement each run in their own per-phase worktree and /aind:approve-plan / /aind:complete retire it. Run every command from a terminal in the main checkout — it stays on the integration branch and drives the worktree by path; parallelism is just opening a second main-checkout terminal. Absent or enabled:false is a strict single-tree no-op.

"worktree": {
  "enabled": true,                       // the on/off switch
  "worktreeRoot": ".claude/worktrees",   // where per-phase worktrees are created (gitignore it)
  "copyFiles": [                         // gitignored files a fresh worktree lacks
    ".claude/aind.env",
    ".claude/settings.local.json",
    ".env"
  ],
  "symlinkDirs": ["node_modules"]        // heavyweight dirs SHARED with the main checkout
}

symlinkDirs links each listed directory into the worktree — a junction on Windows (no admin) or a symlink on Unix — so one install serves every worktree, and teardown removes only the link. It's genuinely shared state (a dependency change means one re-install; a concurrent install can disturb another build), so if you need true per-branch isolation, use pnpm instead and leave symlinkDirs out. Parallel PRs can collide, so the review loop handles merge conflicts automatically: the reviewer flags a PR that no longer merges cleanly, and the coder rebases + resolves and hands back for a fresh review.

telemetry block (usage tracking)

Optionally record raw usage onto each story's work item: a per-model, per-token-type breakdown plus wall-clock time. AIND stores raw numbers only — no cost, no rate card; pricing is done offline against the stored data, so you can re-price history anytime.

"telemetry": {
  "enabled": true,
  "durationField": "Custom.AindDurationSec"   // optional numeric ADO field for elapsed seconds; omit to record only tokens
}

Each of /aind:intake, /aind:plan, /aind:approve-plan, /aind:implement, and /aind:complete then, at its end, attaches a JSON record to the work item (the token breakdown — input / output / cache-write / cache-read, per model) and adds its seconds to the numeric field if configured. Measurement reads the agent host's on-disk session log, so it works on both hosts — Claude records the full per-model breakdown; Copilot records output tokens only (its logs expose no per-message model or input/cache). It's best-effort and fully inert until enabled; it never blocks a phase. The token field needs no ADO field — only the optional time field is an ADO admin step (the plugin can't create fields).

aind.env

Secrets and per-user overrides, gitignored. Two variables:

VariableMeaning
AZURE_DEVOPS_EXT_PAT ADO Personal Access Token — scopes Work Items (r/w) + Code (r/w). Required when the tracker or code host is ADO. Read automatically by az and reused for REST via curl. Never commit it.
AIND_ACTOR Optional. A human-readable actor for the comment signature line. Falls back to git config user.email, then $USER.

Commands

Human entry points, all namespaced /aind:*. Commands are thin: judgment and orchestration only — the deterministic work-item / code-host mechanics live in scripts. The flow is tracked by a single status per work item: Ready for intake → Intake approved / Intake declined → Generating plan → Plan ready for review → Ready for implementation → In implementation → Implementation complete, with Needs attention as the stuck state.

/aind:onboard
pre-flowexisting codebaseno args

The day-one bootstrap for an existing project. Reads existing instruction files and a sample of real source, discovers the rule areas that exist (technical layers, cross-cutting concerns, functional/domain architecture), and drafts .claude/: per-area rules/*.md, a wired CLAUDE.md, project skills for the build/test/run commands it finds, and a copy of the intake rubric. It creates and fills both config files from guided questions, updates .gitignore, and finishes with a preflight report. Everything it writes is a marked DRAFT — review before committing.

/aind:onboard        # run from the project root; no ADO/GitHub auth needed
/aind:kickstart
pre-flowgreenfieldno args

The greenfield twin of onboard. With little or no code to scan, it elicits the project's shape through a guided conversation (functional → architectural → operational, plus any design docs), then drafts the same .claude/ config. Its defining rule: it never invents a convention to fill a gap — an undecided point becomes an explicit TODO, not a rule. It proposes the whole .claude/ tree for your approval before writing. Re-run /aind:onboard once real code exists to reconcile the drafts.

/aind:kickstart      # run from the new project root
/aind:research "<topic>"
pre-storywarmweb search

An optional thinking aid before a story exists. It researches technical approaches for a topic and writes the findings as a markdown file for you to review. It grounds in your codebase first (rules, skills, real source, pinned toolchain) so the actual stack steers the research, then uses web search to check current package versions, official docs, and alternatives — citing every source. The findings document the options explored, the paths discarded and why, trade-offs, risks, open questions, and a recommendation; it asks clarifying questions when the topic is ambiguous or contradicts the codebase. Output is markdown at research.dir (default .aind/research, gitignored), one file per topic. It suggests — it changes no status, opens no PR, and never creates the story; author that next with /aind:new-item or in your tracker.

/aind:research "options for background job scheduling"
/aind:new-item
file tracker only"[title]"

Creates a new work item in the local-file tracker through a short guided Q&A. It assigns an id, scaffolds the markdown file (with status Ready for intake), fills in the Title / Description / Acceptance criteria / Dependencies you provide, and hands it back for review — it never invents requirements and never starts the flow. On the ADO tracker it stops and points you to Azure DevOps Boards.

/aind:new-item "Add CSV export to the reports page"
/aind:intake <id>
phase 0warmgate

The readiness gate. Scores the story against the project's rubric (.claude/intake-rubric.md) — objective criteria are pass/fail, judgment criteria are advisory — and records a signed verdict comment with a per-criterion table and a 0–100 readiness score. A separate dependency gate declines the story if a linked predecessor isn't implemented yet, orthogonal to the score (a story can score 100 and still be declined). It suggests fixes but never edits the story. Sets status to Intake approved or Intake declined.

/aind:intake 1234
/aind:plan <id> [attended|headless]
phase 1warmcreate + revise

Turns an approved story into an implementation plan at plans/<id>/plan.md, delivered as its own PR (with AB# linking and an AIND-LINKS block). The plan carries fixed sections — keep-it-simple / non-goals, acceptance-criteria coverage, an ordered task breakdown that cites the rules/*.md each task must obey, a test strategy, and a definition of done — and posts each assumption / open question as a resolvable review thread. A re-run on a story that already has an open plan PR enters revise mode: it folds the PR's feedback into the same PR (never opens a second, never resolves threads — that's your merge gate). Sets status to Plan ready for review.

Run modes: headless never blocks (every genuine choice becomes a thread); attended co-forms the plan live (a short spar over the key assumptions); the plan artifact is identical either way. The argument wins over planning.mode.

/aind:plan 1234
/aind:plan 1234 attended
/aind:approve-plan <id>
phase 2 close-outhuman-run

Run after you have approved and merged the plan PR. Approval is a human act; this command only records the result: it confirms the plan PR is merged (refuses otherwise — the branch's resolve-all-comments rule guarantees each assumption was addressed), sets status to Ready for implementation, and cleans up the plan branch. Approving also ratifies the planner's test strategy. If plan review surfaced a story-level problem, don't approve — close the plan PR and re-tag the story Ready for intake.

/aind:approve-plan 1234
/aind:implement <id>
phase 3warm codercreate + revise

Builds the merged plan into a code PR, then drives an independent code review to a verdict. It grounds from the merged plan, the cited rule files, project skills, and real code; implements the task breakdown; authors the tests the plan's strategy called for; polishes in-context; and gets the project build and its tests green before opening the PR (with AB# linking + an AIND-LINKS block including the plan-PR URL). It then spawns the cold reviewer for up to three passes, fixing or rebutting each blocking finding. A re-run on a story with an open code PR enters revise mode: it applies only your PR steering (a picked suggestion, a tiebreak verdict, a touch-up), replies on threads, and re-reviews. Status stays In implementation throughout; scope ends at reviewer approval or a human tiebreak — it does not merge.

/aind:implement 1234
/aind:complete <id> [pr-number]
close-outhuman-runterminal

Run after the code PR is reviewer-approved and merged. It verifies the PR is merged (refuses otherwise — it never tags an unmerged PR), writes the terminal Implementation complete status, posts a signed completion note (PR URL + merge commit), and cleans up the merged branch — in that order, so a failed tag-write leaves the item recoverable. It finds the PR by searching on the work-item id; pass an explicit [pr-number] if a story has more than one matching PR. It does not merge; it records the merge you already made.

/aind:complete 1234
/aind:complete 1234 57      # when a story has multiple matching PRs
/aind:dream
dreaming phasecross-storyno args

Orchestrates one improvement cycle. As agents run they emit lessons-learned to the aind/lessons branch; /aind:dream gathers that exhaust, has a cold dreamer cluster it into recurring patterns and judge each (severity × recurrence × factualness), lets you curate the clusters (gate 1), then turns approved ones into one PR against the project's .claude config (gate 2) for you to accept or reject. The dreamer only ever touches the config layer — rules, skills, the rubric, project agent prompts — never the flow; structural findings become a parking-lot note, not a diff. Run it standalone from a clean main checkout.

/aind:dream
/aind:map-states "[work-item-type]"
ADO tracker onlyoptional

Configures the native-State mirror so an ADO work item's built-in State field follows the AIND phase — for board-readers (PMs, functionals) who don't open the repo. It discovers your process's existing States and maps each AIND status onto one that already exists; it adopts existing states, never creates or forces new ones. The result is written as stateMap in aind.settings.json. Re-runnable anytime your States change. On the file tracker there's no separate native State, so it stops and says so.

/aind:map-states "User Story"

Agents (sub-agents)

The flow's two cold roles — independent checks, each spawned as a separate invocation re-grounded from artifacts only, so their judgment isn't contaminated by the work they check. You don't invoke them directly; a command spawns them.

aind-reviewer
coldread-onlyspawned by /aind:implement

The independent reviewer of a code PR. /aind:implement spawns it (up to three passes) with only a work-item id and PR number — never the coder's reasoning. It re-grounds from the PR diff, the merged plan, and every project rule and skill, then challenges the implementation: spec alignment, scope creep, data contracts, rule/skill compliance, cross-cutting concerns, correctness/edge cases, and — because the coder authored its own tests — test coverage and fidelity. It also reads whether the PR still merges cleanly into the integration branch and flags a conflict.

Findings are classified CRITICAL / WARNING (both block) / SUGGESTION (taste-level, non-blocking), each citing file:line. It posts resolvable inline threads + a summary comment and returns a verdict — CLEAN, CHANGES_REQUESTED, or CANNOT-REVIEW. Its independence is structural: it can't edit, commit, push, or run the build/tests (a won't-build / won't-pass is a finding to report, not something it runs). It never authors fixes and never rubber-stamps.

aind-dreamer
coldspawned by /aind:dreamanalyze + author

The independent synthesiser for the dreaming phase. /aind:dream spawns it twice: once in analyze mode — it re-grounds from the accumulated lessons plus the current .claude config, clusters the lessons by underlying issue, judges each with a severity / recurrence / factualness rubric plus a confidence label, and returns the clusters (no edits); then, after you curate, in author mode — on a fresh branch it makes the smallest .claude edit that resolves each approved cluster.

Its authority is hard-bounded to the config layer. Four things are always out of bounds (→ a parking-lot note instead): the flow itself (status model, gates, AIND operational rules), its own guardrails (settings + enforcement/signing hooks), secrets (aind.env), and anything outside .claude/ (product code). It tells a guardrail from an in-scope file by purpose, not name.

Skills

Deterministic, reusable wrappers over the scripts layer. Agents call these to perform work-item and PR mechanics; they're tracker- and code-host-agnostic where relevant, and config is auto-loaded from .claude/.

aind-workitem

Fetches a work item as normalized JSON — id, title, description, acceptanceCriteria, state, dependsOn, links. Read-only; used by an agent to ground itself in a story before scoring or planning it. Works with either the Azure DevOps Boards or the local-file tracker.

aind-status

Sets the AIND status on a work item — the one sanctioned way to transition a story's phase. A work item carries exactly one status: on ADO a single AIND status - <state> tag swapped atomically (and optionally mirrored to the native State), and in the file tracker the state: front-matter field.

aind-comment

Posts a signed comment to a work item — reasoning, a verdict, advisory notes, or a stuck-state trail. This is the only sanctioned comment path: the script always appends the agent's signature so posts stay attributable under one shared identity (on ADO a hook blocks any raw comment that bypasses it). It renders a limited markdown subset (headings, lists, bold, code, pipe tables).

aind-plan-pr

Opens the plan PR for a story and posts each assumption / open question as its own resolvable review thread, then supports the revise loop (read feedback, reply, push). Used by /aind:plan. The agent never resolves threads — that's the human's merge gate.

aind-preflight

Checks the local environment for the AIND prerequisites — required tools, auth, AIND_* config, and best-effort connectivity — and prints a PASS/WARN/FAIL/MANUAL checklist. Read-only; it reports, never gates (always exits 0). Two items are MANUAL (can't be auto-verified): the Azure Boards ↔ GitHub integration and the branch's resolve-comments rule.
