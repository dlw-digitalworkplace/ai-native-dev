Setup guide

Getting started

Set up AIND on a project and run a story through the flow. The smart order is onboard first — it only reads your code and writes draft config (no auth needed), then tells you exactly what's left to wire up.

Choose your agent host

AIND runs on two agent hosts. Pick yours — the install step and a couple of Windows notes below change with it; everything else is identical.

i AIND has three independent per-project choices: the agent host (above), the code host where PRs live (GitHub or Azure DevOps Repos), and the work-item tracker where stories live (Azure DevOps Boards or local files). They're orthogonal — the code-host and tracker choices are set in config (next), not by the toggle above. See the Config reference for every option.

Prerequisites

Most of these are checked automatically by /aind:onboard's preflight probe, which reports what's missing — so you can run onboarding first and fix these afterward.

Tools

  • az (with the azure-devops extension), git, curl, jq, bash — always.
  • Plus the code-host CLI: gh on the GitHub code host, or az repos (the azure-devops extension) on the ADO code host.

Install jq: winget install jqlang.jq (Windows) · brew install jq (macOS) · apt install jq (Linux).

Code-host authentication

GH GitHub code host: gh authenticated as an account that can access your repo — verify with gh repo view <owner>/<repo> (gh auth login / gh auth switch if needed).
ADO ADO code host: nothing extra — the ADO PAT below just needs Code (Read & Write) in addition to Work Items; the forge adapter reuses it for the ADO Repos PR/comment APIs (no separate GitHub auth).

Azure DevOps authentication (work items)

A Personal Access Token with Work Items (Read & Write) + Code (Read & Write). It goes in .claude/aind.env as AZURE_DEVOPS_EXT_PAT — the scripts read it from there. (Not needed if you use the local-file work-item tracker and the GitHub code host.)

Native work-item linking

  • GitHub code host: connect the Azure Boards ↔ GitHub integration so a PR mentioning AB#<id> links to the work item. Confirm with a test PR.
  • ADO code host: nothing to set up — the PR links to the work item natively.

Comment-resolution merge gate

On your integration branch, this is what makes the planner's assumption threads block the plan-PR merge until you resolve them:

  • GitHub: enable branch protection "require conversation resolution before merging".
  • ADO: add a branch policy that requires all comments to be resolved before completion.

Test suite in CI (recommended once you have one)

The per-story gates check tests before a code PR is opened — the coder builds and runs the suite green, and the reviewer reads the tests for coverage and fidelity — but nothing re-runs the suite on the merged integration branch. When you adopt CI, wire your project's test/e2e skills into it and enable "require status checks to pass" on the integration branch. Until then, running the suites between stories is a manual habit, not an enforced gate.

Validate — run the preflight

A read-only probe checks the tools, auth, config, and connectivity above and prints a PASS / WARN / FAIL / MANUAL checklist. It never changes anything.

  • In a session (easiest): ask it to "run the AIND preflight check". It also runs automatically as the last step of /aind:onboard.
  • From a terminal, run it from your project root (so it auto-loads .claude/aind.env): 
    bash <plugin-dir>/scripts/aind-preflight.sh

Resolve every [FAIL] before running the flow. [WARN] is usually config you haven't filled in yet; [MANUAL] items (the Boards↔GitHub integration and the branch rule) can't be auto-verified — confirm those by hand.

▲ Windows + GitHub Copilot CLI: Copilot's shell tool is PowerShell, but AIND's mechanics are Bash scripts — so Git's bash must be the one that resolves in the shell that launches copilot. Two traps: the Git installer only puts Git\cmd (no bash) on PATH, and Windows ships a WSL bash.exe in System32 that shadows Git's bash. Because System32 is on the machine PATH, appending Git\bin isn't enough — Git's bash must come first. Prepend it in your PowerShell profile, then open a new terminal and verify: 
$env:PATH = "C:\Program Files\Git\bin;" + $env:PATH   # in your $PROFILE
(Get-Command bash).Source   # must be Git's bash, NOT System32\bash.exe
Without this, Copilot may improvise the ADO/GitHub calls in PowerShell — bypassing comment signing and the single-status rule.

1 · Load the plugin

Run your agent host from the root of the project you're onboarding — the plugin scaffolds into that project's .claude/.

Load it remotely (no local copy) or from a local clone:

# Remote — loads the published release for this session:
claude --plugin-url https://github.com/dlw-digitalworkplace/ai-native-dev/releases/latest/download/aind.zip

# …or local, if you've cloned the plugin:
claude --plugin-dir <plugin-dir>   # the dir containing .claude-plugin/plugin.json

Install the plugin once (it persists across sessions), then run copilot from the project root:

copilot plugin install dlw-digitalworkplace/ai-native-dev   # from GitHub
# …or from a local clone (a local install is a snapshot — re-install after updates):
copilot plugin install "C:/path/to/ai-native-dev"

Make sure Git's bash wins on PATH first (see the Windows note above).

Confirm it loaded: type /aind — you should see the namespaced commands (/aind:onboard, /aind:intake, …). Bare /onboard won't resolve.

2 · Bootstrap the config

Two entry points, depending on whether the project already has code:

/aind:onboard — existing codebase

Reads the codebase — existing instruction files (.github/copilot-instructions.md, AGENTS.md, cursor/windsurf rules, …) and a sample of real source — discovers the rule areas that actually exist (technical layers, cross-cutting concerns, functional/domain architecture), and drafts into .claude/: per-area rules/*.md, a wired CLAUDE.md, project skills for the build/test/run commands it finds, and a copy of the intake rubric. If it spots competing conventions it asks you to pick one. It finishes with a preflight checklist.

It also creates and fills .claude/aind.settings.json and .claude/aind.env from a few guided questions (tracker, ADO org/project, code host, worktrees, telemetry) and appends the .gitignore lines. No ADO/GitHub auth is needed for this step. When it's done, review and edit the drafts (marked AIND ONBOARDING DRAFT) before committing.

/aind:kickstart — new / greenfield project

Nothing to scan yet, so it elicits the project's goals, architecture, and conventions through a guided conversation (point it at any design docs you have), then drafts the same .claude/ config — marking anything you haven't decided yet as a TODO rather than guessing. Re-run /aind:onboard later, once real code exists, to reconcile those drafts against the codebase.

Fill in config

Onboarding leaves just one manual step: paste your ADO PAT. Config lives in two files under .claude/:

  • .claude/aind.settings.json — shared project config (tracker, ADO org/project, code host, repo, integration branch, worktree/telemetry blocks). Checked in so the whole team gets it.
  • .claude/aind.env — secrets + per-user overrides. Gitignored. Replace the AZURE_DEVOPS_EXT_PAT="<pat>" placeholder with a real PAT.

The scripts auto-load both files (walk-up from the working directory), so you don't source anything — just run the commands from inside the project. Re-run the preflight to confirm everything is green. Every setting is documented in the Config reference.

+ Optional features, all off by default and configured in aind.settings.json: git-worktree parallelism (drive several stories from one clone), usage telemetry (per-phase raw token + time onto the work item), and the native ADO State mirror. See the Config reference for each.

3 · Run the flow

Create a story and set its status to Ready for intake — in Azure DevOps Boards, or (on the file tracker) with /aind:new-item. Then drive it through the phases:

CommandPhaseEffect
/aind:intake <id>0 Score the story; check its dependencies are implemented; post a signed verdict + score; set status → Intake approved / Intake declined.
/aind:plan <id>1 Write plans/<id>/plan.md; open the plan PR (AB#, AIND-LINKS); post assumptions as resolvable threads; status → Plan ready for review.
/aind:approve-plan <id>2 After you approve and merge the plan PR: status → Ready for implementation.
/aind:implement <id>3 Build from the merged plan; open the code PR; drive the cold reviewer to a verdict. Status stays In implementation.
/aind:complete <id>close-out After you merge the code PR: verify the merge, then set Implementation complete.

A declined story is edited and re-tagged Ready for intake, which re-runs intake. Plan-review revisions happen in the PR and don't change the status. Each command is documented in full — with arguments and examples — in the Commands reference.

End-to-end check: run /aind:intake on an under-designed story (expect a decline with the failing criteria), fix it, re-run (expect approval + a single status). Then /aind:plan, and confirm the plan PR carries the AIND-LINKS block, a native AB# link, and one resolvable thread per assumption — and that branch protection blocks the merge until threads resolve. Merge, then /aind:approve-plan. Finally run /aind:implement and confirm it opens a code PR while the status stays In implementation.

Troubleshooting

/onboard (or any command) doesn't appear

Commands are namespaced — use /aind:onboard, not /onboard. Type /aind to list them. Still nothing? (Local) confirm the plugin dir contains .claude-plugin/plugin.json; (remote) confirm the zip URL returns HTTP 200; validate with claude plugin validate <plugin-dir> (one warning about a root CLAUDE.md is expected and harmless); launch with --debug for load errors.

aind-comment / aind-status fail with jq: command not found

Install jq (see Prerequisites) — the runtime needs it to build JSON.

ADO calls fail with auth errors

Ensure AZURE_DEVOPS_EXT_PAT is set in .claude/aind.env (auto-loaded) and the PAT has Work Items + Code read/write. Auto-load is skipped when AIND_ADO_ORG is already set in your shell — if you exported stale values earlier, unset it or use a fresh shell.

Scripts fail with $'\r': command not found

The scripts must be LF, not CRLF. .gitattributes enforces *.sh eol=lf; if you hit this, run git add --renormalize . && git checkout -- scripts hooks.
